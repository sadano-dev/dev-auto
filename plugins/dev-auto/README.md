# dev-auto

tsumiki のスキルを土台に、指示文・GitHub issue URL・メモファイルのいずれかから、マージできる状態の PR までを一気通貫で自律的に進める開発パイプラインです。

## 概要

`dev-auto` は、普通の指示文・GitHub issue URL・メモファイルのいずれか 1 つを入力として受け取り、オープンな PR を出すところまで進めます。流れは、要件の詳細化、外部仕様の合意、`tsumiki:dev-plan` / `dev-run` / `dev-verify`、デバッグと再テストを繰り返す Web テスト（画面開発のときだけ）、複数パスのコードレビュー、任意の UAT 試験項目の作成、PR 作成、公式 `code-review` プラグインの実行と結果コメントの投稿です。tsumiki のスキルを部品として組み合わせ、実装を始める前だけユーザーに質問します。外部仕様に合意すれば、あとは PR まで無人で進みます。

## 前提条件

| 必要なもの | 必要になる場面 | 無い場合 |
|---|---|---|
| tsumiki プラグイン（`/plugin marketplace add classmethod/tsumiki` のあと `/plugin install tsumiki@tsumiki`） | パイプライン全体（dev-context、dev-plan、dev-run、dev-verify、dev-webtest、dcs 系スキル） | dev-auto がインストール手順を伝えて終了します |
| `gh` CLI（認証済み。`gh auth login`） | フェーズ 11 の PR 作成 | PR 作成をスキップし、代わりに手動用の `git push` / `gh pr create` コマンドを `pr.md` に書き出します |
| `code-review@claude-plugins-official`（任意） | フェーズ 11 の公式レビュー | 公式レビューを実行する代わりに、「未インストール」のコメントを PR に投稿します |
| Playwright（Docker Compose または Playwright MCP プラグイン）（任意） | フェーズ 8 の webtest。`ui: true` かつ `ui_runtime: browser` のときだけ | webtest をスキップし、その旨を PR 本文に記載します |

## 使い方

```
/dev-auto:dev-auto <指示文 | GitHub issue URL | メモファイルのパス>
/dev-auto:dev-auto <topic>
/dev-auto:dev-auto
/dev-auto:dev-auto --uat <指示文 | GitHub issue URL | メモファイルのパス>
/dev-auto:dev-auto --auto <指示文 | GitHub issue URL | メモファイルのパス | topic>
```

- 指示文・issue URL・メモファイルを渡した場合: 新しい run を始めます。未完了の run が既にあるときは、新規に始めるか再開するかを尋ねます。未完了の topic に関係がありそうなとき（同じソースファイル、または画面・機能・データが重なる場合）は、新しい topic にするか、既存の topic に区切り（slice）を追加するかを尋ねます（下の「大きな要件: ロードマップと区切り」を参照）。
- topic 名（`docs/dev-auto/roadmaps/<topic>/` のディレクトリ名と完全に一致するもの）を渡した場合: その topic の次に着手できる区切りを始めます。
- 引数なしの場合: **この worktree** にある `docs/dev-auto/*/state.md` のうち、更新が最も新しい未完了の run を再開します。無ければ、全 topic（旧形式を含むすべてのロードマップ）から次に着手できる区切りを集めます。候補が 1 つならそのまま始め、複数なら AskUserQuestion で選んでもらい、1 つも無ければ使い方を表示します。
- `--uat` を付けた場合: PR の前に UAT（ユーザー受け入れ試験）の試験項目フェーズを加えます。フラグが無くても、入力に UAT・受け入れ試験の明示があれば同じ扱いにします。
- `--auto` を付けた場合: 全自動モードです（下記を参照）。フラグが無くても、入力に明示（「全自動で最後まで」「承認なしで」）があれば同じ扱いにします。

### 全自動モード（`--auto`）

各ステップを確認できないとき（例: 時間制限のあるイベント）向けです。dev-auto は最初に全自動でよいかを AskUserQuestion で **1 回だけ** 確認し、`state.md` に `auto_approve: true` を保存して（再開した run も同じモードのままにするため）、以降は何も訊きません。

- refine: 対話の壁打ちはしません。Claude が入力から足りない点を補い、仮定を明記した短い `prd.md` を書きます。増分開発の進め方も Claude が選びます。
- 関係判定・分割の判断と仕様の質問（デザインの方向性、対象デバイス、モックアップの範囲）: 推奨の選択肢を自動で採ります。
- spec: 仕様ドキュメントはすべて作成します。ユーザーの承認の代わりに、自己レビューを 1 パス（PRD との整合、ドキュメント間の整合、実現性）行って問題を直し、仕様を `agreed_by: auto` として記録します。`hands_on` は `false` に固定されます。
- git: 新しいブランチは自動で切りますが、コミットされていない変更がある場合（無関係な作業を巻き込まないため）、ディレクトリが git リポジトリでない場合（`git init`）、破壊的または取り消せない操作が避けられない場合は、**止まって訊きます**。
- PR のあとでロードマップに残りの区切りがあれば、`--auto` では次の区切りを自動で始めます（前の区切りの PR がまだマージされていないときは、そのブランチの上に積みます）。ロードマップが終わるまで続きます。
- 最終報告にはすべての PR を載せ、見直してほしい主な判断を目立たせます。判断はすべて各 run の `decisions.md` に残り、仕様はあとから見直せるよう `spec/` に残ります。

`--auto` を付けなければ、動作は変わりません。

デフォルトブランチで始めた場合、dev-auto は `dev-auto/<run-id>` を作ります。それ以外のブランチで、デフォルトブランチより進んだコミットが無ければそのブランチを使い回します。そのブランチに独自のコミットが既にある場合は、そこで続けるか、デフォルトブランチから新しく切るかを尋ねます。

## パイプライン

| # | フェーズ | 実行内容 |
|---|---|---|
| 1 | intake | `detect-env.sh` による前提条件の確認。issue 入力なら `gh issue view`。`run_id`、`input.md`、ブランチを作成 |
| 2 | context | `tsumiki:dev-init`（マニフェストの無い新規プロジェクト）または `tsumiki:dev-context`（`docs/dev/context.md` が古い、または無い場合） |
| 3 | refine | 入力を 5 点（目的 / スコープ / 振る舞い / 受け入れ条件 / データ）で確認し、入力の形ではなくその結果で分岐する。5 点すべて揃っていれば `dev-auto:refine --gate`（品質チェックのみで質問なし）。そうでなければ AskUserQuestion を 1 回出す。アイデア出しから始める（`dev-auto:ideate`。入力がテーマ・課題だけのとき推奨）か、要件を詰める（`dev-auto:refine`。具体的な機能・変更が書かれているとき推奨）か。ideate を選んだ場合は、続けて refine の品質チェックを通す。結果は `prd_path`（と `state.md` の `refine_mode`、`ideas_dir`） |
| 4 | spec | `dev-auto:spec`。外部仕様を起こし、ユーザーの明示的な合意を得る（対話と自律の境目となる関門） |
| 5 | plan | `tsumiki:dev-plan`。`ui: true` なら `tsumiki:dev-screen-spec from-plan` も実行 |
| 6 | implement | plan の全タスク ID 範囲に対して `tsumiki:dev-run` |
| 7 | verify | `tsumiki:dev-verify`。失敗時は `tsumiki:dev-debug` を最大 2 ラウンド |
| 8 | webtest — 画面確認（画面開発のみ） | `ui_runtime: browser`: `tsumiki:dev-webtest-plan` → `tsumiki:dev-webtest`、その後、未解決のエラーが無くなるまで `tsumiki:dev-debug webtest` → `tsumiki:dev-webtest retest` を最大 3 ラウンド。`ui_runtime: native`: 主要な画面遷移に対する入力駆動の統合テストと、ディスプレイが使えるときはウィンドウのスクリーンショットをモックアップと比較。`hands_on: true` のときは、続けてユーザー自身による動作確認（下記を参照） |
| 9 | review | `dev-auto:review-loop`。複数のレビューパスと修正を、再確認パスで「直すべき指摘」が出なくなるまで繰り返す |
| 10 | uat（`--uat` のときのみ） | 新規・変更した機能に絞った `tsumiki:uat-test-design`。出力は `docs/uat/<yyyymmdd>/` にコミット |
| 11 | pr | `dev-auto:pr-finalize`。push して PR を作成し、PR の CI 結果を確認し、使えれば公式 `code-review` プラグインを実行して、結果コメントを投稿する |

## 対話と自律

フェーズ 1〜4 は対話フェーズです。dev-auto は質問することがあり、フェーズ 4（`dev-auto:spec`）では、外部仕様（機能一覧、画面遷移、デザインシステム、HTML モックアップ、データモデル）にユーザーが明示的に合意（「承認」）するまで、実装には進みません。これが唯一の関門で、無言や曖昧な返事を合意とみなすことはありません。

画面開発では、spec のステップでまずデザインシステムを決めます。アプリ既存のテーマやトークンを流用するか、入力で指定された色に従うか、そうでなければ質問を 1 つ出します（シンプルな既定を推奨します）。既定では、すべての画面モックアップが PC（1280px）幅とスマホ（375px）幅の両方で成り立つ必要があります。仕様を提示するとき、dev-auto は `spec/mockups/index.html` をブラウザで自動的に開きます（`open` / `xdg-open` / `start`。失敗したときだけコマンドの表示にフォールバックします）。各画面を両方の幅で並べて表示し、両方 / PC のみ / スマホのみを切り替えるボタンが付いています。

### 画面の設定

画面開発の run では、`state.md` に 4 つの設定を記録します。既定値は上で説明した Web アプリの動作のままなので、典型的な Web の run で新しく訊くことはありません。

| 設定 | 値（左端が既定） | 決める場面 | 効果 |
|---|---|---|---|
| `ui_runtime` | `browser` / `native` / `none` | intake。`ui` と一緒に決める | UI が描画される場所。`native` はデスクトップアプリ、モバイルネイティブ、ゲームエンジン、組み込みなど、ブラウザ外で描画される UI を指し、その場合フェーズ 8 は Playwright の代わりに代替の確認を行う。`ui: false` のときは `none` |
| `target_devices` | `pc+phone` / `pc_only` / `fixed:<WxH>` | spec（入力に書かれていないときだけ訊く） | `pc_only` と `fixed` は 375px の要件を外す。`fixed` のモックアップは <W>×<H> のステージ上に作って収まるよう拡縮し、ビューアはその 1 サイズだけを表示する |
| `mockup_style` | `designed` / `wireframe` | spec（「モックアップで見た目も合意しますか？」。デザインの質問とは別に訊く） | `wireframe` は要素・レイアウト・文言・状態だけを合意する。デザインシステムはグレースケールの仮テーマになり、各モックアップにワイヤーフレームである旨のラベルが付く |
| `hands_on` | `false` / `true` | spec（「実装後に自分で動かして確認しますか？」。承認時に 1 回だけ訊く） | `true` にすると、フェーズ 8 にユーザー自身による動作確認が加わる |

HTML では表現できない内容の画面（canvas、3D、リアルタイム描画、グラフや地図の中身）は、モックアップの代わりに、参考画像・表示要素の一覧・パラメータ表（サイズ、速度、タイミング）で合意し、`spec/README.md` に「HTML 非対応画面」として列挙します。

### 動作確認（hands-on）

`hands_on: true` のとき、フェーズ 8 は自動確認のあとに 1 回だけ止まります。dev-auto はアプリを起動し（ユーザーの端末でしか動かないものは起動コマンドを表示し）、受け入れ条件と画面の状態から作ったチェックリストを示します。そして結果を AskUserQuestion で尋ねます。修正は合意した仕様の範囲内に限ります。修正と再確認は最大 2 ラウンドで、残ったものは `pr.md` の未解決事項に回します。これは自律フェーズで唯一予定されている停止で、自動テストでは判断できない操作感や使い勝手の確認に役立ちます。業務アプリでも同じです。

`spec_status` が `agreed` になると、`state.md` の `autonomous` フラグが `true` に切り替わり、フェーズ 5〜11 は何も訊かずに進みます（spec の間にユーザーが選んだ場合の動作確認は除きます）。tsumiki のスキルが本来なら選択を求めてくる場面（例: dev-plan の Lightweight / Full-spec の選択、dev-run のエスカレーション対応）では、dev-auto が `skills/run/references/autonomous-policy.md` に従って自分で答え、その判断をすべて `docs/dev-auto/<run-id>/decisions.md` に記録します。また、1 ターンのまま完了報告まで進み続けます。呼び出したスキル（`security-review`、`code-review`、`simplify`、tsumiki の各スキル）の報告は、そのスキルの最終結果として扱い、記録したうえですぐ次のステップに進み、そこでターンを終えません。バックグラウンドで動くスキルやサブエージェント（例: 組み込みの `code-review --fix`）は、結果を `Agent "..." finished` という 1 回きりの完了通知として後から届けます。dev-auto はこの通知を最終結果とみなし、続きを待たずにすぐ先へ進みます。こうした通知を待ってターンを終える前に、停止の見張りとして 10 分のバックグラウンド `sleep` を仕掛けます。タイマーが鳴った時点でサブエージェントがまだ無応答なら（例: 公式 code-review の観点別エージェントのひとつが、自分の子エージェントを待ったまま止まっている場合）、dev-auto は SendMessage で、委譲をやめて今ある結果を報告するよう伝えます。2 回目のタイムアウトではそのエージェントを止め、その観点を未完了（タイムアウトであり、「指摘なし」ではない）として記録して先へ進みます。例外は次の場合だけです。合意した外部仕様そのものが満たせない場合（ある画面が要件を満たせない、データモデルに致命的な矛盾がある）、または取り消せない・コストの大きい判断が避けられない場合（本番データの移行、有料の外部サービス、公開済み API の破壊的変更）は、そこで止まり、`autonomous` を `false` に戻して、AskUserQuestion で尋ねます。

どのフェーズでも、ユーザーへの質問は必ず、推奨の選択肢を先頭にした AskUserQuestion で行います。返事を黙って待つだけの平文の質問はしません。

## スキル

| スキル | 役割 | 単独での利用 |
|---|---|---|
| `dev-auto:run` | `/dev-auto:dev-auto` から呼ばれるオーケストレーター。フェーズ 1〜11 を進め、`state.md` を管理する | 入口専用 |
| `dev-auto:spec` | 足りない外部仕様のドキュメント（機能一覧、画面、モックアップ、データモデル、外部インターフェース）を作り、ユーザーの合意を得る | 可 — 「この要件の外部仕様を固めて合意したい」 |
| `dev-auto:review-loop` | ブランチの差分に対して、観点（バグ、仕様適合、セキュリティ、簡潔さ）を変えながらレビューパスを回し、毎パス修正して再テストする | 可 — 「PR を出す前にこのブランチを何度かレビューして」 |
| `dev-auto:pr-finalize` | ブランチを push して PR を作成し、公式 `code-review` プラグインがあれば実行して、必ず `### Code review` コメントを残す | 可 — 「PR を作って公式レビューまで」 |
| `dev-auto:design-explore` | 既存アプリについて、方向性の異なるデザインのモックアップを並べ、ユーザーの反応から組み合わせ・比較して、決定を記録する | 単独のみ — 「このアプリのデザインの方向性を 10 案くらい見せて」 |
| `dev-auto:ideate` | 一発の発散生成。テーマ・課題、制約、任意の評価基準から、方向性の異なる N 案（既定 5）を出す。各案は 5 点に加え、テーマ・基準への適合、AI の役割、デモの見せ場、削る順番を持つ。そのうえで採点基準つきの比較表と推奨を示し、ユーザーは AskUserQuestion で選ぶ（組み合わせ・編集、もう 1 ラウンドも可） | 可 — 「このテーマで何を作れるか 5 案出して」 |
| `dev-auto:refine` | 5 点の PRD を作る。各点を「ある / 弱い / 無い」で評価し、弱い・無い点だけを訊く（AskUserQuestion 1 回につき最大 4 問。推奨の回答は入力とコードベースから導く）。品質チェック（検証できる受け入れ条件、主な項目つきのエンティティ名、やらないことの明示）を通してから `prd.md` を書く。tsumiki の `feature-rubber-duck` / `incremental-dev` による深掘りも任意で行える | 可 — 「この要望を PRD にして」 |

スラッシュコマンドは `/dev-auto:dev-auto` の 1 つだけです。プラグインのコマンドは `<plugin>:<command>` の名前空間付きなので、`/dev-auto` だけでは不明なコマンドとして扱われます。`/dev-auto:run` でも同じパイプラインが始まります。サブスキルは、説明文に合う自然言語のフレーズで起動するか、Skill ツールから `dev-auto:spec`、`dev-auto:review-loop`、`dev-auto:pr-finalize`、`dev-auto:design-explore`、`dev-auto:ideate`、`dev-auto:refine` として明示的に呼び出します。

## デザイン方向性の検討

`dev-auto:design-explore` は、アプリがおおむね動いていて、見た目やブランディングを決めたい段階向けです。パイプラインの一部ではなく、直接依頼して使います（例: 「デザインの方向性を 10 案くらいモックアップにして」）。

1. アプリの実際のデザイントークン、コンポーネントのマークアップ、データの形を読み、現行デザインを忠実に再現した `00-current.html` を書きます。ダミーデータは、難しいケースを最初から含めます。複数のグループ、エラー、空の状態、長いタイトル、未設定やフォールバックの値です。
2. 対象に合う方向性を約 10 個選びます（暗い劇場風、エンティティごとの色、高密度の一覧、画像主体のギャラリー、エディトリアル、ポップ、モノクロ + アクセント 1 色、ブランド / ロゴ、中核の概念の可視化、モバイルファーストのアプリ）。サブエージェントが並列で、主にトークンと CSS を変えた `00` のコピーとして作ります。
3. どのページも、同じ 2 画面を PC 1280px とスマホ 375px で並べて表示します。各ページには、プロジェクトのトークンファイルとのトークン差分、測定したコントラスト、その方向性を採用したときの影響のメモも付きます。
4. すべてのフレームで横方向のはみ出しとコンソールエラーを確認し、スクリーンショットをレビューして、サムネイルつきの `index.html` ギャラリーを作ります。ギャラリーはローカルで配信し、ブラウザで自動的に開きます（検証用サーバーがまだ動いていれば再利用します）。
5. ユーザーの反応から、組み合わせの案を追加します。ブランドカラーのような未決の値には、候補を比べられるよう、ページ内に切り替えスイッチを付けます。また、方向性によってユーザーが設定する要素が増える場合は、設定画面も追加します。
6. 決定したら、切り替えスイッチを外し、メモを「決定・理由・見送った案」に書き直します。そのうえで、次の run が読む場所に決定を記録します。`roadmap.md` の共通の決定事項、`design-system.md`、またはギャラリーページです。

出力は `docs/design/<yyyymmdd>-<slug>/` に置かれるため、2 回目のラウンドが 1 回目を上書きすることはありません。検討用のボードは、書体も比較対象のひとつなので Google Fonts を読み込むことがあります。`dev-auto:spec` のモックアップは自己完結のままです。

## 大きな要件: ロードマップと区切り

入力が 1 つの PR には大きすぎる場合、dev-auto は詳細化の直後に分割を提案します。次のいずれかに当てはまると、大きすぎる要件とみなします。

- 新規画面が 4 つ以上
- Must の機能が 9 つ以上
- 独立したサブシステムが 2 つ以上
- 技術スタックなど、プロジェクト全体にかかわる未決事項があり、それ専用の検証ステップが必要
- PRD またはその目次自体が、段階的な展開を求めている

大きな要件ごとに、それぞれ **topic** を持ちます。再開するときに再び入力する名前です（2〜3 語の kebab-case。分割に合意したときに確認します）。別の worktree で別の要件に対して dev-auto を動かせば、2 つの topic を並行して進められます。同じ区切りを 2 つの worktree で同時に作業する想定はありません（下の「進行中の作業の確認」を参照）。

分割に合意すると、dev-auto は後続の run の入口となるファイルを書きます。

```
docs/dev-auto/roadmaps/<topic>/roadmap.md           # 区切りの一覧・状態・PR 番号・区切りをまたぐ決定事項
docs/dev-auto/roadmaps/<topic>/slices/01-foundation.md
docs/dev-auto/roadmaps/<topic>/slices/02-<slug>.md  # 区切りのファイル 1 つが、それだけで 1 回の run の入力になる
```

今回の run は、新しい topic の区切り 01 だけを作ります。再開は次のとおりです。

| 実行するもの | 始まるもの |
|---|---|
| `/dev-auto:dev-auto`（引数なし。この worktree に未完了の run が無いとき） | 全 topic から着手できる区切り — 候補が 1 つならそのまま始め、複数なら AskUserQuestion で選び、1 つも無ければ使い方を表示 |
| `/dev-auto:dev-auto <topic>`（`docs/dev-auto/roadmaps/<topic>/` のディレクトリ名と完全に一致） | その topic で番号が最も小さい、着手できる区切り |
| `/dev-auto:dev-auto docs/dev-auto/roadmaps/<topic>/slices/03-<slug>.md` | 指定した区切りそのもの |

区切りが「着手できる」のは、未着手で、前提（`depends_on`）がマージ済みか既に PR があり、ほかの誰も作業していない（下記を参照）ときです。区切りがすべてマージ済みまたは中止になった topic は、候補から外すだけです。あとの topic がその共通の決定事項や仕様を参照するかもしれないので、ディレクトリは残ります。

### 新しい要件を既存の topic に関連づける

分割を提案する前に、dev-auto は新しい要件が未完了の topic に関係していそうか（同じソースファイル、または画面・機能・エンティティの重なり）を確認します。関係していそうなら、規模にかかわらず必ず、新規に始めるか（推奨。関連する topic の共通の決定事項と仕様は読みますが、改めて訊き直しはしません）、既存の topic に区切りを追加するかを尋ねます。新規に始めた場合は、関連する topic のロードマップのパスを `state.md` の `related_roadmaps` に記録し、spec のステップは、その topic で合意済みの決定を蒸し返さずに決定済みとして扱います。

### 進行中の作業の確認

区切りの `status`（未着手 / 進行中 / PR 作成済み / …）は、それに取り組んでいるブランチの中にしか無く、今のブランチのロードマップは古い可能性があります。区切りを始める前に、dev-auto は `scripts/slice-claims.sh <区切りのファイルのパス>` を実行します。これはローカル・リモートのすべてのブランチにあるそのファイルのコピーを読み、ブランチごとに、status、run id、worktree（チェックアウトされていれば）、オープンな PR、そして有効な占有とみなせるかを報告します。これから始める区切りそのものに `claim=yes` が付いていれば開始を取りやめ、どのブランチ / worktree が持っているかを伝えます。同じ topic の *別の* 区切りに `claim=yes` が付いている場合は注意喚起にとどまり、dev-auto が尋ねます（推奨: そのまま進める）。あとから行う roadmap.md の更新が相手の更新と衝突するかもしれませんが、それは後から入る PR 側で解消します。

複数の区切りにまたがる決定（スタック、DB、認証、デザインシステム）は、`roadmap.md` の「共通の決定事項」に記録します。後続の区切りはそれと、前の区切りの合意済み仕様を再利用するので、spec のステップでは、その区切りで新しく出てきたことだけを訊きます。

`pr-finalize` は、区切りのファイルと `roadmap.md`（status と PR 番号）を同じ PR の中で更新します。最終報告の末尾には、次の区切りを始めるコマンド `/dev-auto:dev-auto <topic>`（旧形式のレイアウトなら次の区切りファイルのパス）が示されます。

### 旧形式のレイアウト

topic ができる前は、dev-auto は `docs/dev-auto/roadmap.md` と `docs/dev-auto/slices/` に直接書いていました。リポジトリに既にこれがある場合、dev-auto はそれを **名前の無い 1 つの topic** として扱い、自動で移行も移動もしません（別の worktree が、まさにそのパスに対して区切りの途中かもしれないためです）。候補の集計や関係の確認ではロードマップのタイトルで対象に含まれますが、入力すべき topic 名が無いので、パスで指定します。`docs/dev-auto/roadmap.md` または `docs/dev-auto/slices/NN-*.md` です。新しい大きな要件を自動でこれに追記することはありません。関係の確認で、ユーザーが明示的に「区切りを追加する」を選んだときだけです。

旧形式のロードマップを topic のレイアウトに移したい場合は、手動で行います。しかも、その区切りがどこでも進行中でないとき（オープンな PR が無く、別の worktree でチェックアウトされているブランチも無いとき）に限ります。先に各区切りファイルに対して `scripts/slice-claims.sh` で確認してください。

```
mkdir -p docs/dev-auto/roadmaps/<topic>
git mv docs/dev-auto/roadmap.md docs/dev-auto/slices docs/dev-auto/roadmaps/<topic>/
```

そのあと、移動した各区切りファイルの `roadmap:` フロントマターと、roadmap.md の `- topic:` の行を新しい場所に合わせて直し、通常の PR でリネームを取り込みます。

## run ディレクトリの構成

`/dev-auto:dev-auto` を 1 回実行するごとに「run」になり、`docs/dev-auto/<run-id>/` の下に専用のディレクトリを持ちます（`<run-id>` = `YYYYMMDD-<kebab-case-slug>`）。

```
docs/dev-auto/<run-id>/
├── state.md              # フェーズの進み具合と主なパラメータ（唯一の正）
├── input.md               # 正規化した入力（指示文 / issue 本文 / メモの内容）
├── decisions.md           # 全自動モードで Claude が代わりに決めたこと
├── spec/                  # 外部仕様（dev-auto:spec が作成）
│   ├── README.md           # 目次と合意の記録
│   ├── features.md         # 機能一覧
│   ├── screen-flow.md      # 画面一覧と遷移図（画面開発のみ）
│   ├── design-system.md    # CSS 変数のデザイントークン（画面開発のみ）
│   ├── mockups/*.html      # 静的 HTML モックアップ、PC とスマホ幅（画面開発のみ）
│   ├── data-model.md       # エンティティと ER 図
│   └── api.md              # 外部 IF（API / CLI / イベント。該当する場合）
├── webtest-log.md          # フェーズ 8 の画面確認の記録: webtest の反復・ネイティブの確認・ユーザーによる動作確認の結果（画面開発のみ）
├── review-log.md           # dev-auto:review-loop のパスごとの記録
└── pr.md                   # PR 番号・URL と公式レビューの結果
```

tsumiki 自身の出力は既定のパス（`docs/dev/context.md`、`docs/dev/plans/<plan_name>/`、`docs/dev/webtests/`、`.dcs/`）に残り、`state.md` からパスで参照されます。`uat: true` のときは、`tsumiki:uat-test-design` も `docs/uat/<yyyymmdd>/`（tsumiki の既定の出力先）に書き出します。

## review-loop のパス

| パス | 観点 | 実行内容 |
|---|---|---|
| 1 | バグ / 正しさ | 組み込みの `code-review` スキル、`high --fix <branch>` |
| 2 | 仕様適合 | 実装を `spec/`（features、screen-flow、mockups、data-model）と突き合わせるサブエージェント |
| 3 | セキュリティ | サブエージェント内で実行する組み込みの `security-review`（「最終返信がレポート」というルールで実行が終わってしまわないようにするため）。Web アプリでは `tsumiki:ipa-security-check --diff` も実行 |
| 4 | 簡潔さ / 重複 | 組み込みの `simplify` スキル |
| 5 以降 | バグ / 正しさ（再確認） | `code-review medium --fix` |

各パスの指摘は、直すべき / 先送り / 誤検知に振り分けます。再確認パス（#5 以降）で直すべき指摘がゼロになるまで続け、最大でも合計 6 パスです。上限に達した時点でまだ直すべき指摘と、先送りした仕様改善の提案は、`review-log.md` に書き、`pr.md` の「未解決」セクションに引き継ぎます。

## PR コメントの動作

`pr-finalize` は必ず `### Code review` コメントを残します。公式の `code-review@claude-plugins-official` プラグインは、指摘が無いと何も投稿しないため、dev-auto のコメントが無いと、問題の無い PR がレビューされていないように見えてしまうからです。

- **指摘なしで、公式のコメントも無い場合** — dev-auto 自身が `### Code review` を投稿し、指摘が無かったことと、レビューしたコミットを明記する
- **指摘がある場合** — dev-auto が各指摘をコードと照らして確認し、実際の問題を直して push し、変更内容をまとめた `### Code review 対応` を投稿する
- **対象外の場合**（クローズ済み / ドラフト / 軽微な変更 / レビュー済み） — 公式レビューが実行されなかった理由を短く説明するコメントを投稿する
- **未インストールの場合** — 公式プラグインが使えない旨のコメントを投稿する

dev-auto は、PR をドラフトとして開くことも、force push することも、マージすることも決してありません。

## 補足

- tsumiki に `dev-retest` スキルは無く、フェーズ 8 の再テストのステップは `tsumiki:dev-webtest retest` を使います
- dev-auto は `code-review ultra`（有料でユーザーが起動するクラウドレビュー）も、その `--post` フラグも起動しません
- tsumiki のスキル（dev-plan、dev-run、dev-verify、dev-webtest など）は、必ずメインコンテキストから Skill ツール経由で呼び出し、サブエージェントの中からは呼びません。`dev-run` は内部で自分のサブエージェントを起動するため、サブエージェントの中に入れ子にはできません
- `git stash` は、委譲されたサブエージェントを含め、一切使いません
