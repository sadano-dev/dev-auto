# 外部仕様の作成と合意（spec）

実装に入る前に「外から見てどう動くか」をユーザーと合意するためのスキル。既存資料を探し、足りない資料だけを作り、ユーザーが「承認」と言うまで直す。合意した資料は、以後の自律実装で判断の根拠になる。

## いつ使うか

- dev-auto:run のフェーズ 4 から、引数 `<run-id>` 付きで呼ばれたとき
- 引数に `--auto` があるとき（dev-auto:run の全自動モードから `<run-id> --auto` で呼ばれたとき、または state.md の `auto_approve: true`）は、下の「全自動モード」の差分を当てはめる。それ以外の動きは変わらない
- 単独で「この要件の外部仕様を固めたい」と言われたとき。この場合は引数の要件（指示文 / ファイル）から run-id を作り、`docs/dev-auto/<run-id>/` を作業場所にする（state.md は作らなくてよい）

前提:

- `docs/dev-auto/<run-id>/state.md` があれば Read し、`prd_path`・`ui`・`ui_runtime`・`project_kind` を使う（`ui_runtime` が無ければ `browser`）。`target_devices`・`mockup_style`・`hands_on` はこのスキルで決めて state.md に書く。state.md が無い単独利用では、決めた値を README.md に書く
- state.md に `roadmap` がある（分割した要件の区切りの run）場合は、roadmap.md の「共通の決定」と、前の区切りの run の `docs/dev-auto/<run-id>/spec/`（roadmap.md の run 列から辿る）を読む。前の区切りで合意済みの内容（画面・データモデル・デザインシステム・スタックなど）は「既存を参照」として扱い、作り直したり訊き直したりしない。この区切りで新しく増える・変わる部分だけを作り、合意を取る
- state.md に `related_roadmaps` がある（関係判定で「新しく始める」を選んだ run）場合も、そこに書かれた各 topic の roadmap.md の「共通の決定」と、リンク先の前の区切りの spec を読み、既に決まっている内容として扱う（訊き直さない）。ただし読むだけで、この run の決定はここには書かない（後述の合意の記録は state.md の `roadmap` にだけ書く）
- state.md の `spec_status` がすでに `agreed` → 「外部仕様は合意済みです」と1行伝えて何もせず戻る

## 進め方

鉄則: 仕様を決めるのはユーザー。Claude は分かりやすい資料を作って見せ、指摘を反映するところまでを担当する。合意の言葉が無いまま「合意済み」にしない。

### 1. 必要な資料を決める

`references/spec-templates.md` を Read する。そのうえで、要件（`prd_path` / input.md）から今回必要な資料を決める。

| 資料 | 必要なとき |
|---|---|
| 機能一覧 `features.md` | 常に |
| 画面一覧・遷移 `screen-flow.md` | `ui: true` |
| デザインシステム `design-system.md` | `ui: true` |
| HTML モックアップ `mockups/` | `ui: true`（新規画面・見た目が変わる画面だけ。変わらない画面は作らない。HTML で表せない画面は手順4の「HTML 非対応画面」） |
| データモデル `data-model.md` | 保存するデータ・スキーマ・状態遷移が新しくできる、または変わる |
| 外部 IF `api.md` | API・CLI・Webhook など外から見える入出力が新しくできる、または変わる |

### 2. 既存資料を探す

サブエージェント（Explore、haiku 目安）に、次を並列で探してもらい、パスと要約だけを返してもらう。

- 機能一覧・要件定義: `docs/` 配下の requirements / features / 機能一覧、`.dcs/*/prd*.md`、`docs/dev/plans/*/requirements.md`
- 画面: `docs/dev/screen-specs/_index.md`（tsumiki の画面仕様）、ルーティング定義（`app/`・`pages/`・`routes` など）、既存のモックアップや Figma リンク
- データ: Prisma schema、SQL マイグレーション、ORM モデル、型定義、ER 図
- 外部 IF: OpenAPI / GraphQL スキーマ、ルートハンドラ、CLI 定義
- デザイン: CSS 変数・テーマ・デザイントークン、共通コンポーネント

見つかった資料が今回の範囲を十分に説明していれば「既存を参照」として README に載せ、作り直さない。今回の変更で足りない部分だけを新規・差分として作る。

### 3. デザインシステムを決める（`ui: true` のとき）

見た目の方向性は、必要なときだけユーザーに訊く。あわせて、下の「対象デバイス」と「モックアップで合意する範囲」も決める（`mockup_style: wireframe` のときは、この表の質問は訊かず仮テーマにする）。

| 状況 | やること |
|---|---|
| ロードマップの「共通の決定」（`roadmap` または `related_roadmaps` の roadmap.md）にデザインシステムがある（前の区切り・関係する topic で決定済み） | 訊かない。その design-system.md を参照し、足りないトークンだけを足す |
| 既存アプリにテーマ・CSS 変数・デザイントークン・UI ライブラリの設定がある | 訊かない。手順2で見つけた値を design-system.md に写す（方針: 既存アプリ準拠） |
| 入力（指示文・issue・PRD）に色・雰囲気・ブランドの指定がある | 訊かない。指定どおりに作る（方針: ユーザー指定） |
| 上のどちらでもない（新規で指定なし） | AskUserQuestion で1回だけ訊く（下記） |

訊くときの内容:

- 質問:「画面の見た目（デザインの方向性）はどうしますか？」
- 選択肢1:「シンプルにおまかせ（Recommended）」（説明: 白基調の中立色＋アクセント1色。あとから変更しやすい）
- 選択肢2:「メインカラーを指定する」（説明: 次の入力で色コードか色名を書いてください）
- 選択肢3:「参考サイト・雰囲気を指定する」（説明: URL や「やわらかい」「業務的」などを書いてください）
- 選択肢4:「ダークモードにも対応する」（説明: シンプルな配色で、ライト / ダークの両方を用意する）

回答に合わせて `references/spec-templates.md` の「design-system.md」の形式で `design-system.md` を作る。指定された色がコントラスト基準（WCAG AA）を満たさない場合は、色味を保ったまま明度を調整し、調整したことを手順5で伝える。

#### 対象デバイス（`target_devices`）

どの画面幅・解像度に合わせるかを決める。ロードマップの「共通の決定」にあれば訊かない。入力・既存アプリ（Web のレスポンシブ対応、ネイティブアプリの対象プラットフォーム・ウィンドウ設定など）から判断できればそれに従う。判断できなければ AskUserQuestion で1回訊く。

- 質問:「対象とする画面はどれですか？」
- 選択肢1:「PC とスマホの両方（Recommended）」（説明: PC 幅 1280px とスマホ幅 375px の両方で崩れないようにする）
- 選択肢2:「PC のみ」（説明: スマホ幅は対象外。PC 幅 1280px で確認する）
- 選択肢3:「固定解像度の画面」（説明: Other に基準解像度を書いてください。例: 1280x720）

| 値 | モックアップと確認 |
|---|---|
| `pc+phone`（既定） | 従来どおり。PC 幅 1280px とスマホ幅 375px の両方で崩れないこと |
| `pc_only` | PC 幅 1280px だけで作り、確認する。「375px で崩れない」要件と確認は外す |
| `fixed:<WxH>` | 基準解像度 <W>×<H> のステージを作り、ウィンドウに合わせて縦横比を保って縮小表示する。「375px で崩れない」要件と確認は外す |

#### モックアップで合意する範囲（`mockup_style`）

上のデザインの質問とは別に、見た目まで合意するかを決める。ロードマップの「共通の決定」にあれば訊かない。入力で「ワイヤーフレームで」「見た目は後で」などの指定があれば訊かずに `wireframe` にする。既存アプリにテーマがあり、それに従う場合は訊かずに `designed` にする。それ以外は AskUserQuestion で1回訊く。デザインの方向性の質問より先に訊き、`wireframe` になったらデザインの方向性は訊かない。

- 質問:「モックアップで合意するのは見た目まで含めますか？」
- 選択肢1:「見た目も含めて合意する（Recommended）」（説明: 配色・文字・余白まで、モックアップどおりに実装する）
- 選択肢2:「要素・配置だけ合意する（ワイヤーフレーム）」（説明: 見た目は仮のまま。画面に何がどこにあるかだけを決める）

`wireframe` のとき、design-system.md は「仮テーマ（グレースケール等）・見た目は合意対象外」として作り、デザインの質問は訊かない（コントラストの確認は行う）。モックアップは画像・グラデーション・装飾を使わず、各画面に「ワイヤーフレーム：要素と配置の確認用」と表示する。

決めた `target_devices` と `mockup_style` は、state.md があれば書き込む。

### 4. 資料を作る

作業場所は `docs/dev-auto/<run-id>/spec/`。state.md があれば `spec_status: drafting` にする。

1. **features.md** を最初に作る。以後の ID はこれに合わせる
2. **screen-flow.md** と **data-model.md**、**api.md** を作る（必要なものだけ）
3. **mockups/** は画面ごとにサブエージェント（sonnet 目安）へ並列で依頼する。依頼には次を渡す
   - `references/spec-templates.md` の「mockups/」の節をそのまま
   - `design-system.md` の全文（トークンを `:root` にそのまま書いて使うこと）
   - その画面の screen-flow.md の節と、関連する features.md の節
   - 遷移先の画面 ID とファイル名の一覧（リンクをつなぐため）
   - 対象デバイスの一文。`pc+phone`:「PC 幅 1280px とスマホ幅 375px の両方で崩れないこと。375px で横スクロールを出さないこと」/ `pc_only`:「PC 幅 1280px で崩れないこと」/ `fixed:<WxH>`:「<W>×<H> のステージで作り、ウィンドウに合わせて縦横比を保って縮小表示すること」
   - `mockup_style: wireframe` なら「画像・グラデーション・装飾を使わず、画面に『ワイヤーフレーム：要素と配置の確認用』と表示すること」
   - 「`git stash` を使わない」「指定ファイル以外を編集しない」
4. 全画面そろったら、`references/mockup-viewer.html` を `mockups/index.html` にコピーし、`TITLE` と `SCREENS` 配列だけを書き換える。`target_devices` が `pc+phone` 以外なら `DEVICES` も書き換える（`pc_only` なら `sp` を消す。`fixed:<WxH>` なら <W>×<H> の1種にする）。これで全画面を対象デバイスの幅で並べて確認できる
5. 可能なら見た目を確かめる。Playwright（`mcp__plugin_playwright_playwright__*` など）が使える場合は、各モックアップを対象デバイスの幅（`pc+phone` なら 1280px と 375px、`pc_only` なら 1280px、`fixed` なら <W>×<H>）で開いてスクリーンショットを撮り、はみ出し・重なり・横スクロールが無いかを見る。問題があれば直す
6. 整合性を自分で確認する: 画面の操作が遷移図と一致しているか、機能一覧の全 Must 機能がどこかの画面か API に現れているか、画面に表示している項目がデータモデルにあるか。ずれていたら直す
7. **README.md** を作り、各資料の状態を表にする。state.md があれば `spec_status: pending` にしてコミットする（`docs(dev-auto): <run-id> external spec draft`）

**HTML 非対応画面**: canvas・3D・リアルタイム描画の画面や、チャート・地図の中身のように、HTML で要素と配置を表せない（表しても合意の役に立たない）部分は、モックアップの代わりに「参照画像（スケッチ・既存画面の撮影・似た画面のキャプチャなど）＋表示する要素の一覧＋パラメータ表（寸法・速度・タイミング・色など、合意したい数値）」を screen-flow.md のその画面の節に書いて合意する。周りの HTML で表せる部分（メニュー・ツールバー・操作パネル・数値表示など）はモックアップを作り、描画部分は枠と注記で示す。README の備考に「HTML 非対応画面: <画面 ID>」と書く。

### 5. ユーザーに見せる

チャットに次をまとめて出す（資料の全文は貼らない）。

- 機能一覧の表（ID・機能名・優先度・区分）
- 画面遷移図（mermaid をそのまま）と画面一覧
- デザインシステムの方針（メイン色と、訊かずに決めた場合はその理由）
- データモデルの要点（エンティティと主な関係）
- 外部 IF の一覧（あれば）
- モックアップ: 下の手順で自動で開いたことと、ファイルのパス（`docs/dev-auto/<run-id>/spec/mockups/index.html`）。対象デバイスが複数なら、上部のボタンで「並べて表示 / PC / スマホ」を切り替えられることも伝える。`wireframe` なら見た目は合意の対象外であること、HTML 非対応画面があればその画面と合意してほしいパラメータ表も伝える
- Claude が仮に決めた点・迷った点（最大5件。「〜と仮定しました」の形で）

`ui: true`（モックアップがある）ときは、AskUserQuestion の前に **Bash でモックアップをユーザーのブラウザで開く**。ユーザーに `! open ...` を打たせない。

- macOS: `open docs/dev-auto/<run-id>/spec/mockups/index.html`
- Linux: `xdg-open <同じパス>`（すぐ戻るのでフォアグラウンドで実行し、終了コードを見る。`$DISPLAY` も `$WAYLAND_DISPLAY` も空なら GUI が無いので実行せず「開けなかった」扱いにする）
- Windows（Git Bash など）: `start "" <同じパス>`
- 終了コードが 0 以外のとき・コマンドが無いとき・GUI が無いときは「開けなかった」とみなし、そのときだけ開き方のコマンドをチャットに示す。出力を捨ててバックグラウンドにすると失敗が見えないので、そうしない
- 修正ループで手順5に戻ったときも、直したあとにもう一度開く（ブラウザで最新の内容が見えるように）

続けて AskUserQuestion で訊く。

- 質問:「この外部仕様で実装に進めてよいですか？合意後は PR 作成まで自動で進めます」
- 選択肢1:「モックアップを見てから答える（Recommended）」（説明: 見終わったら返信してください）
- 選択肢2:「承認して実装に進む」
- 選択肢3:「修正したい点がある」（説明: 次の質問で修正内容を書いてください）

`ui: false`（モックアップが無い）ときは、選択肢1を「資料を読んでから答える（Recommended）」に置き換える。

### 6. 修正ループ

- 「修正したい」→ 修正内容を AskUserQuestion で訊き（直したい資料を選択肢にし、具体的な内容は Other に書いてもらう。選択時のメモに内容が書かれていればそれを使う）、該当資料だけ直し、README の「合意の記録」に1行足して、手順5に戻る
- 「見てから答える」→ そこで待つ。次の返信を手順5の回答として扱う。返信が承認か修正か読み取れないときは、手順5の AskUserQuestion をもう一度出す（平文で訊き返さない）
- 「承認」→ 手順7へ（`ui: true` で `hands_on` が未定なら、先に下の質問を1回だけ訊く）
- 修正が大きく、要件そのものが変わった場合は、features.md から作り直す

`ui: true` のとき、承認を受けたら手順7の前に1回だけ AskUserQuestion で訊き、`hands_on` を state.md（無ければ README.md）に書く。入力で「自分で触って確認したい」などの指定があれば訊かずに `true` にする。

- 質問:「実装後に、ご自身で動かして確認しますか？」
- 選択肢1:「しない（Recommended）」（説明: 従来どおり、PR 作成まで自動で進めます）
- 選択肢2:「する」（説明: 自動の確認のあとで一度止まり、確認チェックリストに沿って動かしてもらいます。指摘は仕様の範囲内で直します）

### 7. 合意を記録する

1. README.md の状態を「合意済み（<日時>）」にし、合意の記録に1行足す
2. state.md があれば `spec_status: agreed` にし、フェーズ4にチェックを付けてログに1行足す
3. state.md に `roadmap` がある場合は、この合意で決まった区切りをまたぐ事項（スタック・DB・認証・デザインシステム・対象デバイス・モックアップで合意する範囲・共通レイアウト・命名規則など）を、その `roadmap` のパスの roadmap.md の「共通の決定」に1行ずつ足す。以後の区切りの記述とずれた場合は、該当する区切りファイルの「着手前の見直しメモ」に1行足す（`related_roadmaps` にある他 topic の roadmap.md には書かない。読むだけの参照）
4. コミットする（`docs(dev-auto): <run-id> external spec agreed`）
5. 呼び出し元（dev-auto:run）へ戻る。dev-auto:run から呼ばれた場合は、ここでターンを終えず、run のフェーズ 5 にそのまま進む。単独利用なら次のステップを案内して終わる

## 全自動モード（`--auto` / `auto_approve: true`）

ユーザーが資料を確認できない前提で、資料は通常どおりすべて作り、ユーザーの承認の代わりに自己レビューで合意扱いにする。手順1〜4（資料の判定・既存資料の探索・資料づくり・整合性の確認）は変えない。違うのは次の点だけ。

- 手順3の質問（デザインの方向性・対象デバイス・モックアップで合意する範囲）は訊かず、それぞれの推奨の選択肢（シンプルにおまかせ / PC とスマホの両方 / 見た目も含めて合意する）を採る。入力や既存アプリから判断できる場合は通常どおりそれに従う。採った値を decisions.md に1行ずつ書く
- 手順5〜6の代わりに **自己レビューを1回** 行う。サブエージェント（opus 目安。「`git stash` を使わない」「spec/ 以外を編集しない」と書く）に spec/ 一式と PRD（`prd_path`）を渡し、次を指摘させる
  - PRD との整合: PRD の目的・スコープ・受け入れ条件が features.md に漏れなく入っているか、スコープ外のものが入っていないか
  - 資料間の整合: 手順4の6と同じ（遷移図と画面、Must 機能の出現、表示項目とデータモデル）
  - 実現性: 期間・既存スタック・外部依存から見て無理のある仕様（実装に大きな未知がある、外部の有料サービスが必須など）が無いか
  指摘を Claude が直す（1回だけ。直しきれない点は README の備考と decisions.md に書く）。モックアップは開かない（Playwright での見た目の確認は通常どおり行う）
- `hands_on` は訊かず `false` にする（自動の確認で代える）。decisions.md に書く
- 手順7で、README の状態を「自動合意（<日時>・自己レビュー済み）」にし、合意の記録に「全自動モードで自動合意。自己レビューで直した点: …」と1行足す。state.md は `spec_status: agreed` と `agreed_by: auto` にする。decisions.md に「spec を自動合意」と1行足す
- 鉄則（仕様を決めるのはユーザー）と「ユーザーの明示的な承認なしに agreed にしない」は、全自動モードでは「`--auto` でユーザーが承認を委ねた」ことをもって満たすものとする。`--auto` が無いときに自動合意しない

## やらないこと

- 実装コード・テストコードを書かない
- 内部設計（クラス構成・ファイル分割・ライブラリ選定）を仕様に書き込まない。外から見える振る舞いに絞る
- ユーザーの明示的な承認なしに `spec_status: agreed` にしない（`--auto` の全自動モードだけは例外で、自己レビュー後に `agreed_by: auto` を付けて記録する）
- 平文で質問して返事を待たない（確認はすべて AskUserQuestion で行う）
- 変わらない既存画面のモックアップを作り直さない
