# デザインの方向性の検討（design-explore）

「だいたい実装できたので、見た目を詰めたい」ときに、検討材料となるモックアップを短時間でそろえるスキル。現行デザインを再現した基準（00）と、方向性の違う複数案（01〜）を、同じ内容・同じ画面・同じ幅で並べる。ユーザーが気に入った要素を組み合わせた案を作り、決めきれない値は画面上で切り替えて比べ、決まったことを記録するところまでを担当する。

## いつ使うか

- サービスの実装がある程度進み、ブランディング・見た目の方向性を決めたいとき
- 「デザイン案を何個か見たい」「この案とこの案を組み合わせて」「色を比べたい」と言われたとき
- dev-auto:spec のデザインシステムより踏み込んで、書体・配色・レイアウトの方向性そのものを比較したいとき

前提:

- 画面の見た目を持つプロジェクト（Web / アプリ）であること。無ければ「見た目の検討対象がありません」と伝えて終わる
- 実装がまだ無い新規プロジェクトの見た目決めは dev-auto:spec のデザインシステム手順を使う

## 進め方

鉄則: デザインを決めるのはユーザー。Claude は比べやすい材料を作り、反応を反映し、決まったことを記録する。案は「気に入った要素を案をまたいで組み合わせる」前提で作る。

### 1. 範囲を決める

次を自分で決め、手順 5 の報告で「〜と仮定しました」として伝える。ユーザーの指示に数・画面・方向が書かれていればそれに従う。

| 項目 | 既定 |
|---|---|
| 案の数 | 10 案 ＋ 現行の再現 00 |
| 画面 | 2 画面。「入口の画面（トップ・一覧）」と「サービスの中心になる画面（詳細・再生・編集など）」 |
| 幅 | PC 1280px とスマホ 375px を横に並べる（dev-auto:spec のモックアップと同じ幅） |
| 出力先 | `docs/design/<yyyymmdd>-<slug>/`（slug 例: `brand-directions`）。既存の検討があれば別ディレクトリにして上書きしない |

画面の選び方が決めきれないときだけ AskUserQuestion で 1 回訊く（候補の画面を選択肢にし、推奨を先頭に置く）。平文で訊いて返事を待たない。

### 2. 現行を調べ、現行の再現 00 を作る

サブエージェント（Explore、haiku 目安）に次を並列で探させ、パスと要約だけを返させる。

- デザイントークン（`tokens.css`・CSS 変数・テーマ設定・Tailwind 設定など）の全値
- 対象画面のコンポーネントとマークアップ（クラス名・構造・状態ごとの表示）
- 対象画面が表示するデータの形（DB スキーマ・API 応答型）。**実際に保存・取得している項目**を確かめる（持っていない情報をモックに描かない）
- 既存のモックアップ・デザイン資料（dev-auto の `spec/design-system.md`、`docs/dev-auto/roadmaps/*/roadmap.md` と旧形式の `docs/dev-auto/roadmap.md` の「共通の決定」など）

その結果から、ダミーデータ（フィクスチャ）を先に決める。ユーザーに言われる前に「難しい場合」を入れておく:

- 複数のまとまり（例: 複数の元データから集めた一覧はグループごとに見出しが付く）
- エラー・利用不可の項目、空の状態、長いタイトル、未設定（フォールバック）の項目
- 状態の違い（再生中・選択中・いいね済みなど）

`references/board-template.html` をコピーして `00-current.html` を作る（Claude 自身か opus のサブエージェント）。トークンは実プロジェクトの値をそのまま `.app` に書き、マークアップは実コンポーネントの構造に合わせる。以後の案はこの 00 のコピーから作るので、00 のマークアップが全案の共通土台になる。

### 3. 方向性を決めて並列で作る

`references/directions.md` を Read し、サービスの題材・利用者・現行の弱点に合わせて方向性を 10 個選ぶ（候補集は出発点。題材に合わせて差し替える）。各案に「狙い（誰に何を感じてほしいか）」「変える軸」「トレードオフ」を 1 行ずつ決める。

1 案 1 ファイル（`NN-<slug>.html`）で、サブエージェント（sonnet 目安）へ並列に依頼する。依頼文は `references/directions.md` の「サブエージェントへの依頼文」をそのまま使い、次を渡す:

- 00-current.html のパス（コピー元）と、その案の狙い・軸
- フィクスチャの「難しい場合」をその案でどう見せるかを考えること
- 「指定ファイル以外を編集しない」「`git stash` を使わない」

### 4. 検証する

`references/verify.md` の手順で全ファイルを確認し、崩れを直す。

1. ローカルの HTTP サーバーで配信する（Playwright は `file://` を開けないことがある）
2. すべての `.device` で `scrollWidth === clientWidth`（PC 1280 / スマホ 375）であること、コンソールエラーが無いこと
3. スクリーンショットを見て、はみ出し・重なり・不自然な折り返しを確認する。`verify.md` の「よくある崩れ」を先に当たる
4. `references/gallery-index.html` を `index.html` にコピーし、案の配列を書き換え、`shots/NN-pc.jpg` / `NN-sp.jpg` のサムネイルを作る

### 5. ユーザーに見せる

チャットに次をまとめる（HTML の中身は貼らない）。

- 一覧を自動で開いたことと、その URL（下の手順）
- 案の一覧表（番号・名前・1 行の狙い）
- フィクスチャの「難しい場合」を各案がどう見せたか（表）
- 実装に効く注意点（データが足りない・API が要る・運用ルールが要る など、案の採否に関わるもの）
- 仮定した点（範囲・画面・フィクスチャ）

まとめを出す前に、**Bash でサーバーを立ててユーザーのブラウザで一覧を開く**。ユーザーにコマンドを打たせない。

1. 手順4の検証（`verify.md` の「配信する」）で決めたポート `<port>` を使う
2. そのサーバーがまだ応答していればそのまま使う。止まっていれば、同じポートが空いていればそのポートで、塞がっていれば `verify.md` と同じ決め方で選び直して、Bash の `run_in_background` で起動する: `python3 -m http.server -d <出力先> <port>`
3. `curl -s -o /dev/null -w '%{http_code}' http://localhost:<port>/` が 200 を返すまで待ってから開く: macOS は `open http://localhost:<port>/`、Linux は `xdg-open`（`$DISPLAY` も `$WAYLAND_DISPLAY` も空なら実行しない）、Windows（Git Bash など）は `start ""`。どれもフォアグラウンドで実行して終了コードを見る
4. サーバーが 200 を返さない・開くコマンドの終了コードが 0 以外・コマンドが無い・GUI が無いときだけ、開き方のコマンドと URL をチャットに示す
5. 手順6で案を足したり直したりしたあとも、同じ URL をもう一度開く（サーバーは立て直さない）

ユーザーがコメントするのを待つ。反応の読み取りに迷ったときは AskUserQuestion で訊く。

### 6. 反応を反映して絞る

ユーザーの反応に応じて次を行う。どれも既存ファイルを壊さず、新しい番号のファイルを足すか、該当ファイルだけを直す。

| 反応 | やること |
|---|---|
| 「この画面はこういうデータで見たい」 | フィクスチャを直し、全案に同じ変更を入れる（サブエージェントで並列） |
| 「A をベースに B と C を合わせたい」 | 組み合わせ案を新しい番号で作る（Claude 自身か opus）。サイト全体の色とリスト単位の色のように、組み合わせで競合する要素は片方を中立にして、決めた理由をボードのメモに書く |
| 案が新しい設定項目を生む（例: ユーザーが選べるテーマ色） | その設定画面も、実際のフォームの構造に合わせてモックに足す。頼まれずに足したことを報告で伝える |
| 「この値を A / B / C で比べたい」（サービス色など） | 1 ファイル内に切り替えボタンを置き（テンプレートの `.compare-switch`。`body[data-compare]` で値を切り替え、`#値` で初期値を指定）、候補ごとのコントラストを計算してメモに書く。WCAG AA を満たさない候補は色味を保って明度を調整し、調整したと伝える |
| 「ロゴは別で作る」「イラストは要らない」 | ロゴは枠（高さ・マーク＋文字）だけ決めた仮置きにする。スマホで邪魔な装飾は外す |

### 7. 決定を記録する

ユーザーが「これで決定」と言ったら:

1. 比較用の切り替えを外し、決定した値だけを残す。ボードのメモを「決定した値＋理由＋見送った案と理由」に書き換える
2. `index.html` の説明とサムネイルを最新にする
3. 次の開発で読まれる場所に 1 行ずつ記録する。`docs/dev-auto/roadmaps/*/roadmap.md`（旧形式の `docs/dev-auto/roadmap.md` を含む）が複数あれば、どの topic の「共通の決定」に書くかを AskUserQuestion で訊く（選択肢は topic ごと。この案が対象にしたアプリ・画面に近い topic を「(Recommended)」にする）。roadmap.md が1つだけならそこに、無ければ dev-auto の `spec/design-system.md` があればその方針欄に書く。どちらも無ければ出力先の `index.html` の冒頭に「決定事項」を書く
4. コミットはユーザーに頼まれたときだけ行う

## 成果物

- `docs/design/<yyyymmdd>-<slug>/00-current.html`（現行の再現）
- `NN-<slug>.html`（方向性ごとの案。各ファイルに狙い・トークン差分・アクセシビリティ・採用時の影響範囲のメモ付き）
- 組み合わせ案・比較用の案（手順 6 で追加したもの）
- `index.html`（サムネイル付きの一覧）と `shots/NN-pc.jpg` / `NN-sp.jpg`
- 決定事項の記録（roadmap.md / design-system.md / index.html のいずれか）

## 完了チェックリスト

- [ ] 00 は実プロジェクトのトークン値とコンポーネント構造を写している
- [ ] フィクスチャに複数のまとまり・エラー・空・長文・未設定の場合が入っている
- [ ] 各案のメモに、現行トークンとの差分・測ったコントラスト・採用時の影響範囲がある
- [ ] 全ファイルの全 `.device` で横はみ出しが無く、コンソールエラーが無い
- [ ] スクリーンショットを実際に見て崩れを確認した
- [ ] index.html から全案を開け、サムネイルが最新である
- [ ] 決定した事項を、次の開発が読む場所に記録した

## 次のステップ

- 決まった方向性を実装に移す: `/dev-auto:dev-auto <出力先>/NN-<slug>.html のデザインをアプリに適用する` で、トークンの変更と画面の修正を PR まで進められる。仕様の合意から始めたい場合は dev-auto:spec を使う
- 別の観点でもう一度検討する: 新しい出力先で、このスキルをもう一度使う

## やらないこと

- アプリ本体のコード（トークンファイル・コンポーネント）を書き換えない。モックアップだけを作る
- 平文で質問して返事を待たない（確認は AskUserQuestion で行う）
- 実在の他社サービスのロゴ・名称・画面をそのまま模倣しない（「〜風」は雰囲気の参考に留める）
- 案を 1 つに絞るのをユーザーの代わりに決めない。推奨を述べるのはよいが、決定はユーザーの言葉で行う
- 頼まれていないコミット・プッシュをしない。`git stash` は使わない
