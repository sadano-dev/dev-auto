# 全自動モード（`--auto`）

ユーザーが途中の資料や質問に付き合えない（時間が限られている、席を外す）ときのためのモード。外部仕様の合意を含め、対話フェーズの判断も Claude が推奨案で決め、PR まで（ロードマップがあれば全区切りの PR まで）止まらずに進める。決めたことはすべて `decisions.md` に残し、仕様資料（spec/）も通常どおり作るので、ユーザーは後からまとめて確認できる。

`--auto` を付けないときの動きは何も変わらない。このファイルの内容は `auto_approve: true` の run にだけ適用する。

## 有効にする条件

- 引数に `--auto` がある（例: `/dev-auto:dev-auto --auto <指示>`）。`--auto` は入力本文から取り除く
- 入力や呼び出しの指示に「全自動で最後まで」「承認なしで」「確認なしで最後まで」「おまかせで PR まで」などの明示がある
- state.md の `auto_approve: true`（再開時・次の区切りの run。値はそのまま引き継ぐ）

有効なら state.md に `auto_approve: true` を書く。

## 開始時の確認（1回だけ）

新しく `auto_approve: true` で始める run では、intake の最初（detect-env の直後）に AskUserQuestion で1回だけ確認する。再開時、自動で続けて始めた次の区切りの run では訊かない。

- 質問:「全自動モードで最後まで進めます。よろしいですか？」
- 選択肢1:「全自動で進める（Recommended）」（説明: 要件の補完・分割・外部仕様の承認も Claude が推奨案で決めます。決定は decisions.md に、仕様資料は spec/ に残るので後から確認できます）
- 選択肢2:「通常モードで進める」（説明: 外部仕様の合意などを従来どおり確認します）

「通常モード」を選ばれたら `auto_approve: false` にし、以後は通常の手順で進める。これ以降、下の「止まって訊く例外」以外では質問しない。

## フェーズごとの扱い

| 場面 | 通常モード | 全自動モード |
|---|---|---|
| intake: 未コミットの変更がある | 止めるか含めるかを訊く | **止まって訊く**（ユーザーの無関係な変更を run に混ぜないため。例外の1つ） |
| intake: 先行コミットのあるブランチ | 新しいブランチを切るか訊く | 推奨どおり既定ブランチから新しいブランチを切る（記録） |
| intake: 未完了の run がある | 新規 / 再開を訊く | 推奨どおり新規に開始する（記録） |
| 前提: git リポジトリでない | `git init` してよいか訊く | **止まって訊く**（リポジトリの外の状態を変えるため。例外の1つ） |
| context: `tsumiki:dev-init` の質問 | 対話 | 入力と一般的な定番構成から Claude が決める（記録） |
| refine: 5点がそろわないときの ideate / refine の選択 | どちらから始めるか訊く | 推奨（テーマだけなら ideate、具体的な機能があれば refine）を採る（記録） |
| ideate: 案の選択 | 訊く | 推奨案を採る（`dev-auto:ideate --auto`。記録） |
| refine: 5点が足りない | 足りない点だけを訊く（dev-auto:refine） | 訊かない。下の「refine の自動補完」 |
| 関係判定 | 新しく始めるか足すかを訊く | 推奨（関係が強い topic があれば足す、無ければ新しく始める）を採る（記録） |
| 分割判定 | 分割案と topic 名を訊く | 「この分割で進める（Recommended）」と候補の topic 名をそのまま採る（記録） |
| 区切り: 他で同じ topic の別区切りが作業中 | 始めるか訊く | 推奨どおり始める（記録）。同じ区切りが作業中なら着手しない（通常どおり） |
| 区切り: 前提の PR が未マージ | 待つか積むか訊く | 前の区切りのブランチの上に積んで始める（待つと止まってしまうため。記録） |
| spec: デザイン・対象デバイス・モックアップ範囲 | 必要なら訊く | 各質問の推奨案を採る（記録） |
| spec: 合意 | ユーザーの「承認」まで修正ループ | 資料は全部作り、自己レビュー1回で直して `agreed_by: auto` で合意扱い（dev-auto:spec の「全自動モード」） |
| spec: `hands_on` | 訊く | 常に `false`（自動の確認で代える。記録） |
| フェーズ 5〜11 | 自律（従来どおり） | 自律（従来どおり。autonomous-policy.md の原則4に当たるときは止まって訊く） |
| フェーズ 11 のあと、ロードマップに続きがある | 次のコマンドを案内して終わる | 下の「区切りの連続実行」 |

「記録」は decisions.md に1行足すこと（書式は autonomous-policy.md）。フェーズ欄は実際のフェーズ名（intake / refine / spec など）にし、根拠に「auto」と書く。

## 止まって訊く例外

全自動モードでも、次のときだけ AskUserQuestion で訊く（推奨を先頭に「(Recommended)」付き）。

1. 開始時の確認（上記。1回だけ）
2. 未コミットの変更がある（ユーザーの無関係な変更を含めない。`git stash` は使わない）
3. git リポジトリでない（`git init` してよいか）
4. 破壊的な操作が避けられない（force push、ブランチの削除、既存の作業の上書きなど）
5. autonomous-policy.md の原則4（外部仕様を変えないと進めない / 取り返しがつかない・費用や外部への影響が出る判断が避けられない）

## refine の自動補完

フェーズ 3 では `dev-auto:refine` を `<run-id> --auto` で呼ぶ（ideate の案ファイルを通すときは `<run-id> --gate <案ファイル> --auto`）。refine は質問せず、次を行う（詳細は dev-auto:refine の手順 3b）。`tsumiki:dcs:feature-rubber-duck` / `tsumiki:dcs:incremental-dev` は呼ばない（どちらも対話が前提のため）。

1. 入力・既存コード・`docs/dev/context.md` から、足りない点を推測で埋める。迷ったら小さく保守的な案（スコープを狭く、既存の慣習に合わせる）を選ぶ
2. `docs/dev-auto/<run-id>/prd.md` に PRD を書く（5点の見出し＋「仮定」「未決事項」の節。仮定は「〜と仮定した（理由）」の形で1行ずつ）
3. 仮定のうち仕様に効くものを decisions.md に1行ずつ足す
4. 品質チェック（検証できる受け入れ条件・エンティティと主な項目・やらないこと）を仮定で満たす
5. `prd_path` を prd.md に、`refine_mode` を `auto` にする

既存コードへの改修でアプローチが複数考えられるときは、Claude が推奨案を選び、選ばなかった案を prd.md の「検討した他の案」に1行ずつ書く。

## 区切りの連続実行

フェーズ 11 を終えたら、通常の完了報告の代わりに次を行う。

1. state.md に `roadmap` があり、その topic に着手できる区切り（slicing.md の「着手できる区切り」。前の区切りの PR が未マージでも、上の表どおり積んで始める）が残っていれば、「次の区切り <NN> を全自動で始めます」と1行伝え、同じターンのまま `<topic>` を入力にした新しい run を `auto_approve: true` で始める（開始時の確認はしない）
2. 他で作業中などで着手できる区切りが無くなったら、全体の完了報告を出して終わる

## 完了報告（全自動モード）

通常の完了報告の項目に加えて、次を必ず出す。ロードマップを連続実行したときは、全区切りをまとめて1つの報告にする。

- 作った PR の一覧（区切りごとの URL と、積んだ PR は base ブランチ）
- **確認してほしい決定**（最大5件）: decisions.md のうち、仕様や範囲に効く・後から変えにくいもの（refine の仮定、分割、spec の自動合意で決めた点など）を優先し、ファイルのパスと一緒に示す
- 仕様資料の場所（`docs/dev-auto/<run-id>/spec/`、モックアップは `spec/mockups/index.html`）と、自動合意した旨
