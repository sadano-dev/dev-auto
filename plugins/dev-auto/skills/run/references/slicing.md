# 大きな要件の分割（ロードマップと区切りファイル）

1本の PR に収まらない要件（アプリ全体の PRD など）は、PR 単位の「区切り（slice）」に分け、区切りごとに dev-auto の run を1回ずつ回す。続きから始めるための入口として、ロードマップ `roadmap.md` と区切りごとのファイル `slices/NN-<slug>.md` を必ず作る。ユーザーは次の区切りを始めるとき、何を渡すかを考えなくてよい。

ロードマップは **topic** ごとに分ける。1つの大きな要件が1つの topic になる。別の worktree で並行して作業するときは、別の topic を進める前提にする（同じ区切りを2か所で進めないよう、着手前に「他で作業中か」を確かめる）。

## 分割するかの判定

refine（フェーズ 3）のあと、spec（フェーズ 4）の前に判定する。次のどれか1つに当てはまれば「大きい」とみなし、分割を提案する。

- 新しく作る・大きく変える画面が 4 つ以上
- Must の機能が 9 つ以上
- 独立した仕組みが 2 つ以上ある（例: 認証基盤、外部 API 連携、課金、管理画面、バッチ処理）
- 技術スタック・DB・認証など、プロジェクト全体に効く未決事項があり、その検証だけで一区切りになる
- PRD やインデックスの資料自体が「段階的に進める」「フェーズ分け」を示している

当てはまらなければ分割しない（何も作らない）。

## 区切り方

- 1区切り = PR 1本。目安は画面 1〜3 個、または仕組み 1 つ
- 最初の区切りは、あとの全区切りが前提にする **基盤**（スタック・スキーマ・認証・共通レイアウト・デザインシステムなど）にする
- 各区切りは、それだけでテストが通り、動かして確かめられる単位にする（画面だけ・API だけの半端な区切りにしない。シードデータを使ってよい）
- 依存の向きは前から後ろだけにする（後ろの区切りに前の区切りが依存しない）
- 順番は、利用者に価値が届く入口から先にする。資料に「進め方」の順があればそれに従う

## ファイル構成

```
docs/dev-auto/roadmaps/
└── <topic>/
    ├── roadmap.md           # 区切りの一覧・状態・共通の決定（入口）
    └── slices/
        ├── 01-foundation.md # 区切りファイル（dev-auto への入力になる）
        ├── 02-<slug>.md
        └── ...
```

- `<topic>` は英小文字ケバブの短い名前（例: `list-share`）。`/dev-auto:dev-auto <topic>` で打つので、2〜3語にする
- 新しい topic 名は、分割の合意を取る AskUserQuestion で候補を出して確認する（run の slug から作る）。まだマージされていない他のブランチで同じ名前が使われていないか、`git rev-list --all -1 -- docs/dev-auto/roadmaps/<topic>` が空であることを確かめ、使われていれば別の名前を候補にする
- 区切り番号は topic ごとに 01 から振る
- 以下、`<roadmap>` は topic の roadmap.md のパス、`<slices>` はその横の `slices/` を指す

### 旧形式（topic なし）

以前の dev-auto は `docs/dev-auto/roadmap.md` と `docs/dev-auto/slices/` に直接作っていた。これがあるリポジトリでは、**旧形式の topic が1つある** ものとして扱う。

- 移動・改名はしない（別の worktree で進行中の区切りのパスが変わってしまうため）
- 引数なしで始めるときの候補と、関係判定の候補に含める。表示名は roadmap.md のタイトル
- 旧形式には打ちやすい topic 名が無いので、明示するときはパス（`docs/dev-auto/roadmap.md` / `docs/dev-auto/slices/NN-*.md`）で指定する
- 新しい大きな要件を旧形式の roadmap.md に足さない（関係判定で「既存に足す」を選ばれたときだけ足す）

## 新しい topic か、既存の topic に足すか（関係判定）

refine（フェーズ 3）のあと、分割判定の前に行う。区切りファイルが入力の run と、topic 名で続きを指定された run では行わない。

1. 未完了の topic（全区切りが「マージ済み」か「中止」ではないもの。「PR 作成済み」は下の「roadmap.md の形式」の読み方で PR の状態を確かめる）を集める。`docs/dev-auto/roadmaps/*/roadmap.md` と旧形式の `docs/dev-auto/roadmap.md`
2. 次のどれかに当てはまる topic を「関係しそう」とみなす。当てはまるものが無ければ訊かずに次へ進む
   - 元の要件（roadmap.md の「元の要件」）が今回の入力と同じファイル
   - 今回の要件が触れる画面名・機能名・データのエンティティが、その topic の区切りファイルや「共通の決定」と重なる
3. 関係しそうな topic があれば、要件の大きさにかかわらず AskUserQuestion で訊く（topic ごとに1つの選択肢。最大3つ）
   - 「新しく始める（Recommended）」（説明: 小さければ topic を作らない単発の run、大きければ新しい topic。<topic> の共通の決定と spec は参照する）
   - 「<topic> に区切りを足す」（説明: <topic> の未完了の区切り数と、他の worktree で作業中の区切り（下の「他で作業中かの確認」）があればその番号。作業中の topic に足すと roadmap.md の更新がぶつかりやすいことも書く）
4. 結果で分岐する
   - 新しく始める → state.md の `related_roadmaps` に、関係しそうだった topic の roadmap.md のパスを書く。spec はここにある「共通の決定」と前の区切りの spec を参照する（訊き直さない）。続けて分割判定をする
   - <topic> に足す → state.md の `roadmap` にその roadmap.md のパスを書く。分割判定で分割しない大きさでも、区切りを1つ足してこの run の区切りにする。分割する大きさなら、足す区切りすべてを作る。番号はその topic の最後の番号の続きから振り、`depends_on` には既存の区切りも書ける

## roadmap.md の形式

~~~markdown
# ロードマップ: <全体のタイトル>

- topic: <topic>
- 元の要件: <PRD / インデックスのパス>
- 作成: <日付>（run <run-id>）

## 区切り

| # | 区切り | 範囲（画面・機能） | 前提 | 状態 | run | PR |
|---|---|---|---|---|---|---|
| 01 | [基盤](slices/01-foundation.md) | スタック・スキーマ・認証・i18n | - | 進行中 | 20260924-foundation | |
| 02 | [入口 A](slices/02-entry-a.md) | 画面 2, 13 | 01 | 未着手 | | |

状態は「未着手 / 進行中 / PR 作成済み / マージ済み / 中止」のいずれか。

「PR 作成済み」は、その PR がマージされても既定ブランチ上ではそのまま残る（最後の区切りは、後から「マージ済み」に直す run が無い）。そのため状態を読むときは、「PR 作成済み」で `pr` のある区切りを `gh pr view <n> --json state` で確かめ、`MERGED` ならマージ済み、`CLOSED` なら中止として扱う（gh が使えなければ書かれた状態のまま扱う）。topic が完了したか、前提がそろったかの判定はこの読み方で行う。ファイルを直すのは、その topic の区切りの run の中だけでよい。

## 共通の決定

区切りをまたいで効く決定。後の区切りでは、ここに書いたことを訊き直さない。

| 決定 | 内容 | 決めた区切り | 根拠・記録 |
|---|---|---|---|
| スタック | Next.js + OpenNext (Cloudflare) | 01 | docs/dev-auto/<run-id>/decisions.md |
| デザインシステム | docs/dev-auto/<run-id>/spec/design-system.md | 01 | spec 合意 |

## 続きの始め方

次の区切りは `/dev-auto:dev-auto <topic>` で始まる（着手できる区切りから）。続けられる topic がこれだけなら、引数なしの `/dev-auto:dev-auto` でもよい。区切りを指定するなら `/dev-auto:dev-auto docs/dev-auto/roadmaps/<topic>/slices/<NN>-<slug>.md`。
~~~

## 区切りファイル（slices/NN-<slug>.md）の形式

区切りファイルは、そのまま dev-auto の入力になる。refine の5点（目的・スコープ・振る舞い・受け入れ条件・データ）がそろった状態で書き、次の run で refine を skip できるようにする。

~~~markdown
---
slice: "02"
title: 入口 A（リスト公開ページと OGP）
status: 未着手            # 未着手 / 進行中 / PR 作成済み / マージ済み / 中止
depends_on: ["01"]
roadmap: docs/dev-auto/roadmaps/<topic>/roadmap.md
run_id:                   # 着手したら記入
pr:                       # PR を作ったら記入
---

# 02 入口 A（リスト公開ページと OGP）

## 目的
<誰の何を解決するか。全体の中でのこの区切りの役割>

## 範囲
- 対象画面: <元資料の画面番号・名前>
- 対象機能: <機能>
- やらないこと: <次以降の区切りに回すもの>

## 振る舞い
- <主要なユースケースと、その入出力・画面の動き>

## 受け入れ条件
- Given ... When ... Then ...

## データ
- <使う・増えるエンティティ。前の区切りで作ったものは「既存」と書く>

## 読む資料
- <元資料の該当節・画面モックアップ・決定番号>
- 共通の決定: docs/dev-auto/roadmaps/<topic>/roadmap.md の「共通の決定」

## 着手前の見直しメモ
<前の区切りの結果、この区切りで変わったこと。着手時に run が追記する>
~~~

## 続きから始めるときのルール（run のフェーズ 0〜1）

| 渡されたもの | 始める区切り |
|---|---|
| 引数なし（この worktree に未完了の run も無い） | 全 topic の「着手できる区切り」から選ぶ（下記） |
| `<topic>`（`docs/dev-auto/roadmaps/<topic>/` の名前と完全に一致） | その topic の「着手できる区切り」 |
| `<roadmap>`（topic の roadmap.md、または旧形式の `docs/dev-auto/roadmap.md`） | 同上 |
| 区切りファイル（`<slices>/NN-*.md`、旧形式の `docs/dev-auto/slices/NN-*.md`） | その区切り |
| 「次の区切り」「続き」などの指示文 | 引数なしと同じ |

引数が topic 名と完全に一致しなければ、topic 名とはみなさず指示文として扱う。

### 着手できる区切り

次をすべて満たす区切りを「着手できる区切り」とする。

- 状態が「未着手」
- `depends_on` の区切りが「マージ済み」か「PR 作成済み」（PR 作成済みなら、下の手順1でマージを待つか積むかを訊く）
- 他で作業中ではない（下の「他で作業中かの確認」で `claim=yes` が無い）

選び方:

- topic を指定されたとき: その topic の着手できる区切りのうち番号が最も小さいものを、「<topic> の区切り <NN> <タイトル> を始めます」と1行伝えて始める。1つも無ければ、その理由（全部済み / 前提待ち / 他で作業中）を伝えて終了する
- 引数なしのとき: topic ごとに、着手できる区切りのうち番号が最も小さいものを1つずつ候補にする
  - 候補が1つ → 1行伝えてそのまま始める
  - 候補が複数 → AskUserQuestion で選んでもらう（選択肢は「<topic>: <NN> <タイトル>」、説明に残りの区切り数。最大4つ。更新が新しい roadmap の topic を先頭にして「(Recommended)」を付ける）
  - 候補が無い → 使い方（`/dev-auto:dev-auto <指示文 | issue URL | メモファイル | topic>`）と、他で作業中の区切りがあればその一覧を1行ずつ示して終了する
- 状態の「PR 作成済み」は、「roadmap.md の形式」の読み方で PR の状態を確かめてから判定する（前提がそろったか・topic が完了したか）
- 全区切りが「マージ済み」か「中止」の topic は候補にしない（ディレクトリは残す。後の topic が共通の決定や spec を参照するため）

### 他で作業中かの確認

同じ区切りを2つの worktree で進めないために、着手する前に必ず確かめる。区切りの状態は、それを進めているブランチにしかコミットされていないので、今のブランチの roadmap.md だけでは分からない。

```bash
bash "${CLAUDE_PLUGIN_ROOT}/scripts/slice-claims.sh" <区切りファイルのパス>
```

全ブランチ（ローカルとリモート）の区切りファイルを読み、「進行中」「PR 作成済み」になっているブランチを出力する。`claim=yes` は、そのブランチが worktree で checkout されているか open の PR があり、作業中とみなすもの。

- `claim=yes` がある → その区切りには着手しない。「<NN> は <branch>（<worktree>）で作業中です」と伝える。明示して指定された区切りなら終了し、候補選びの途中なら候補から外す
- `claim=no` だけ → 記録が残っているだけ（マージ済みで状態の更新が遅れている、放棄したブランチなど）。着手してよい。open_pr が無く status が「PR 作成済み」なら、手順1で PR の状態を確かめて roadmap.md を直す
- 同じ topic の **別の区切り** が `claim=yes` のとき → 着手はできるが、AskUserQuestion で「このまま始める（Recommended）/ やめる」を訊く（説明: <NN> を <worktree> で作業中。roadmap.md の更新がぶつかる場合は、あとから始めた側の PR で解消する）。topic の全区切りファイルを同じスクリプトで調べて判断する

### 着手するとき

着手するときは次を行う。

1. 前提の区切り（`depends_on`）の状態を確かめる。PR の状態は `gh pr view <n> --json state` で確認し、roadmap.md の状態を実際に合わせて直す
   - すべて「マージ済み」→ 既定ブランチから新しいブランチを切って始める
   - 「PR 作成済み」でまだマージされていないものがある → AskUserQuestion で「前の PR がマージされるまで待つ（Recommended）/ 前の区切りのブランチの上に積んで始める（PR の base をそのブランチにする）」を訊く
2. <roadmap> の「共通の決定」と、前の区切りの `docs/dev-auto/<run-id>/spec/` を読み、区切りファイルの内容とずれていれば区切りファイルを直す（「着手前の見直しメモ」に追記）
3. run のブランチを用意したら（run のフェーズ 1 の手順5のあと。既定ブランチには直接コミットしない）、区切りファイルの `status` と roadmap.md の状態を「進行中」、`run_id` を記入して **すぐに** コミットする（他の worktree の `slice-claims.sh` から見えるようにするため）

## 状態を更新するタイミング

| タイミング | 更新するもの |
|---|---|
| 分割に合意したとき | `docs/dev-auto/roadmaps/<topic>/` に roadmap.md と全区切りファイルを作成（既存の topic に足すときは、その roadmap.md に行を足す）。この run の区切りを「進行中」にする |
| 区切りに着手したとき | 区切りファイルの `status` / `run_id`、roadmap.md の状態・run |
| spec 合意で全体に効く決定をしたとき | roadmap.md の「共通の決定」に1行足す |
| PR を作ったとき（pr-finalize） | 区切りファイルの `status: PR 作成済み` / `pr`、roadmap.md の状態・PR。この更新を同じ PR に含める |
| 前提の PR のマージを確認したとき | roadmap.md の状態を「マージ済み」に |
