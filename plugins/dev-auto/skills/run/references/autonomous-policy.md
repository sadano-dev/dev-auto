# 自律モードの決定ポリシー

外部仕様の合意（`spec_status: agreed`）以降、dev-auto は **ユーザーに質問しない**。tsumiki の各スキルは途中で AskUserQuestion を使う設計になっているが、自律モードではそれを呼ばず、下の表に従って Claude 自身が回答を決め、そのまま次へ進む。

全自動モード（state.md の `auto_approve: true`）では、外部仕様の合意前（対話フェーズ）の判断も Claude が推奨案で決める。その扱いは `auto-mode.md` に従う。合意後の扱いはこのファイルのとおりで変わらない。

## 基本原則

1. **判断の根拠は合意済みの外部仕様**（`docs/dev-auto/<run-id>/spec/`）と `input.md`。仕様に書いてあることは仕様どおりに決める
2. 仕様に書いていない内部設計（ファイル構成・ライブラリの細部・命名など）は、既存コードの慣習 → `docs/dev/context.md` → 一般的なベストプラクティスの順で決める
3. 決めた内容は必ず `decisions.md` に1行ずつ追記する（書式は下記）。ユーザーは後からここを見て、何が自動で決まったかを確認する
4. 次のどちらかに当たる場合だけ、自律モードを中断してユーザーに AskUserQuestion で確認する。それ以外の理由では止めない
   - **外部仕様そのものを変えないと進めない**と判明した（例: 合意した画面では要件を満たせない、データモデルに致命的な矛盾がある）
   - Claude が決めると取り返しがつかない、または費用や外部への影響が出る判断が、避けられない（例: 本番データの移行、有料の外部サービスの契約・課金、公開済み API の互換性を壊す変更）。避けられる場合は避けて進み、pr.md の「未解決事項」に書く

   このほか、spec で合意した `hands_on: true` のとき、run のフェーズ 8 の「人による動作確認」で、ユーザーの操作結果を AskUserQuestion で受け取る（合意済みの工程なので、`autonomous` は `true` のまま）。
5. 破壊的な操作（force push、既存ブランチの削除、本番リソースへのアクセス、共有 stash の pop）はしない

## 止まらずに進めるルール

自律フェーズでは、フェーズ 11 の完了報告まで **1つのターンの中で続けて進める**。途中でターンを終えると、ユーザーが「進めて」と返すまで止まってしまう。

1. **スキルやサブエージェントの報告は、そのスキルの最終結果として受け取り、すぐ次の手順に進む**。`security-review`・`code-review`・`simplify`・公式の `code-review:code-review`・tsumiki の各スキルは、最後にユーザー向けの報告（「〜は見つかりませんでした」「次のステップ: …」など）を出して終わる作りになっている。報告が出た時点で、そのスキルは終わっている（dev-auto 全体としてはまだ途中、というだけ）。内容を review-log.md などに記録し、同じターンのまま次の手順のツール呼び出しに進む。報告を出したところでターンを終えない。スキルの本文に「最後の返答はレポートだけにする」（`Your final reply must contain the markdown report and nothing else.` など）とあっても同じで、dev-auto の中ではレポートを記録すればその指示を満たしたものとする。レポートを返答の最後に置いてターンを終えない。そうした指示を持つスキルのうち、`security-review` は親で直接呼ばず、サブエージェントに実行させる（review-loop の「パス 3」）
2. **スキルが示す「次のステップ」や「〜しますか？」には従わない**。次にやることは dev-auto の手順が決める
3. **平文で質問しない**。「進めてよいですか？」「〜しますか？」と書いてターンを終えるのは禁止。確認が必要なら、原則4に当たる場合だけ AskUserQuestion を使う
4. **進捗は1行で伝え、そのまま次のツールを呼ぶ**（例:「パス 3 のセキュリティレビューは指摘なし。続けて ipa-security-check を流します」）。進捗を伝えただけでターンを終えない
5. ターンを終えてよいのは、(a) フェーズ 11 まで終えて完了報告を出したとき、(b) 原則4で AskUserQuestion を出したとき、(c) 続けられないエラー（gh 未認証で push できない等）で手順どおり終了するとき、(d) 下の「バックグラウンドで動くスキル・サブエージェント」で、完了通知を待つ以外にやることが無いとき、(e) spec で合意した `hands_on` の確認（run のフェーズ 8 の「人による動作確認」）で、AskUserQuestion を出してユーザーの操作結果を待つとき、だけ

### バックグラウンドで動くスキル・サブエージェント

組み込みの `code-review`（`--fix` 付きを含む）など一部のスキルと、Agent ツールで起動したサブエージェントは、バックグラウンドで動く。呼び出した直後に返るのはエージェント名（「〜 is working in the background」など）だけで、結果は後から **完了通知**（`Agent "/code-review medium --fix <branch>" finished` のような1件の通知と、その本文）として届く。

1. **呼び出した直後**: 結果はまだ無い。指摘の有無や内容を推測して記録・コミットしない。並行してできる手順（そのパスの結果に依存しないもの）が無ければ、「<何を> バックグラウンドで実行中。完了通知を待ちます」と1行書いてターンを終えてよい（ルール5の (d)）。ただし、ターンを終える前に必ず下の「止まっていないかの確認」のタイマーを起動しておく。完了通知が届くと自動で次のターンが始まる
2. **完了通知が届いたら、それが最終結果**。バックグラウンドのスキルは途中経過を通知しない。`finished` の通知は1回だけで、その本文がそのスキルの報告のすべてである（下の確認で SendMessage して再開させた場合だけ、再開後にもう1回届く。そのときは新しいほうが最終結果）。「途中報告が届いた」「全体の完了を待つ」と解釈して待ち続けない。通知の本文から指摘と修正内容を読み取り、`git status` / `git diff` で実際の変更を確かめ、テスト・記録・コミットをして、同じターンのまま次の手順に進む
3. **通知がエラーや中断で終わっていたら**（`failed`・`stopped`・本文が空など）、同じ引数で1回だけ呼び直す。それでも駄目ならそのパス・手順を skip として記録し、次へ進む
4. **完了通知が届いたか分からなくなったら**（ターンを再開したときなど）、通知を待つ前に会話の直近のタスク通知と `git log` / `git status` を確かめる。すでに届いていれば、待たずに処理する
5. Bash の `run_in_background` で起動したプロセス（開発サーバーなど）は、終了するまで通知が来ない。起動の完了は、同じターンの中で自分で確かめる（例: `for i in $(seq 60); do curl -sf <url> >/dev/null && break; sleep 2; done` を1回の Bash 呼び出しで回す）。起動を「待つ」ためにターンを終えない

#### 止まっていないかの確認（タイマー）

バックグラウンドのエージェントは、自分の下にさらにサブエージェントを分け、その結果を待ったまま止まることがある（例: 公式 `code-review:code-review` の観点別エージェントの1つが、応答なしのまま終わらない）。このとき完了通知は永遠に来ず、dev-auto も止まる。これを防ぐため、完了通知を待ってターンを終える前に、タイマーを仕掛けておく。

1. **タイマーを起動する**: Bash を `run_in_background` で `sleep 600` を実行する（説明は「<待っているもの> の止まり確認タイマー」）。終わると通知が届き、ターンが再開する。待っているエージェントが複数でも、タイマーは1つでよい。起動したエージェントの名前（または ID）を控えておく
2. **タイマーの通知が届いたら**、待っているエージェントのうち、まだ完了通知が届いていないものを確かめる（`ListAgents` でも確かめられる）
   - すべて届いている → 何もしない（タイマー通知は無視する）
   - 届いていないものがある（1回目）→ それぞれに SendMessage で「これ以上サブエージェントに分けず、まだ確認していない分は自分で読んで、いまある結果で最終報告を返してください。子の結果を待たないでください」と送る。タイマーをもう一度起動してターンを終える
   - 2回目でもまだ届かない → そのエージェントを止め（TaskStop が使えれば使う）、その観点・手順を **未完了（時間切れ）** として記録する。ほかの結果だけで次の手順に進む。未完了の観点は review-log.md や PR コメントに「時間切れで未完了」と書き、「問題なし」として扱わない
3. 待っていたものがすべて完了して次へ進むとき、動いているタイマーは TaskStop で止める。止められなければ、あとで届いたタイマー通知は無視する
4. タイマーの 600 秒は目安。レビュー対象の差分が大きい（変更ファイル 50 以上など）ときは 900 秒にしてよい

## ユーザーに確認するときの書き方（全フェーズ共通）

対話フェーズ（フェーズ 1〜4）でも自律フェーズでも、ユーザーに判断を求めるときは **必ず AskUserQuestion を使う**。

- 選択肢は2〜4個。Claude の推奨を先頭に置き、ラベルの末尾に「(Recommended)」を付ける
- 自由記述が必要な場合も AskUserQuestion を使い、選択肢の説明で「Other に書いてください」と案内する
- 回答を受けたら、そのまま次の手順に進む（「了解しました」だけ返してターンを終えない）

## tsumiki スキルの質問への既定回答

| スキル | 質問 | 自律モードでの回答 |
|---|---|---|
| tsumiki:dev-plan | モード選択（Lightweight / Full-spec） | `ui: true` なら **Full-spec**（dev-screen-spec from-plan と dev-webtest-plan が `acceptance-criteria.md` を必要とするため）。`ui: false` でも機能が3つ以上なら Full-spec、それ以外は Lightweight |
| tsumiki:dev-plan | plan 名の正規化確認 | state.md の `plan_name` をそのまま採用 |
| tsumiki:dev-plan | 曖昧点の確認 | spec/ の記述から回答。記述が無ければ既存コードの慣習に合わせた最小の選択肢を採る |
| tsumiki:dev-plan | 🔴（根拠なし）項目の扱い | spec/ に根拠があれば 🔵 として採用。無ければ保守的な案を採用して decisions.md に記録 |
| tsumiki:dev-run | 範囲外の依存・実装失敗のエスカレーション | 依存タスクを範囲に含めて再実行。2回失敗したら `tsumiki:dev-debug "<エラー>"` を実行してから再試行。それでも駄目ならタスクを `blocked` として残し、PR 本文の「未解決事項」に書く |
| tsumiki:dev-verify | 未完了タスクがあるが続行するか | 続行する（未完了タスクはレポートに残る） |
| tsumiki:dev-screen-spec | 画面一覧・グループ分けの確認 | spec/screen-flow.md の画面一覧どおりに承認 |
| tsumiki:dev-screen-spec | from-plan の衝突（source-wins / plan-wins / merge） | **plan-wins**（合意済み仕様を優先） |
| tsumiki:dev-webtest-plan | 既存計画の上書き確認 | 同じ plan 名のものは上書き、それ以外は残す |
| tsumiki:dev-webtest | 実行環境のセットアップ方法 | すでに起動している Docker Compose の Playwright があればそれ → 無ければローカルの Playwright MCP（`mcp__plugin_playwright_playwright__*`）→ どちらも無ければ Docker Compose で起動を試みる。起動に失敗したら webtest フェーズを skip として記録し、PR 本文に「webtest 未実施（理由）」と書く |
| tsumiki:dev-webtest / dev-webtest-plan | `ui_runtime: native`（ブラウザ外で動く画面）のときの扱い | 実行しない。run のフェーズ 8 の「ブラウザ外で動く画面」（入力を送る統合テストと画面撮影の比較）で確認する |
| tsumiki:dev-debug | 環境・設定の問題 | `.env.example` 等から推測できる値で補う。秘密情報が必要なものは埋めずに skip して記録 |
| tsumiki:uat-test-design | 出力形式 / 出力先 / 対象範囲 | markdown のみ（xlsx なし）/ 既定の `docs/uat/<yyyymmdd>/` / spec/features.md で区分が「新規・変更」の機能と、その関連画面・API に絞る |
| tsumiki:uat-test-design | 抽出結果のレビュー・確認 | そのまま採用し、gaps は pr.md の「未解決事項」に書く |
| 公式/組み込みの code-review | レビューレベル | 明示的に指定する（review-loop の手順どおり）。`ultra` は使わない |

## decisions.md の書式

```markdown
# 自律モードでの決定事項

| 日時 | フェーズ | 質問・論点 | 決定 | 根拠 |
|---|---|---|---|---|
| 2026-09-23T10:12 | plan | dev-plan のモード | Full-spec | ui: true |
```

## 中断するとき

原則4に該当して中断する場合は、state.md の `autonomous` を `false` に戻し、ログに理由を書いてから AskUserQuestion で確認する。回答を spec/ に反映し（必要なら dev-auto:spec の修正ループを回し）、再合意したら `autonomous: true` に戻して、同じターンのまま続行する。
