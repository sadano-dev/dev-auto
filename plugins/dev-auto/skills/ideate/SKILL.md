# アイデア出し（ideate）

テーマや課題から「何を作るか」の候補を **制約をよく効かせた一発生成** で N 案つくり、比べて 1 案を選ぶスキル。案づくりを反復ループやペルソナの多段レビューで回さない。足りなければ「もう 1 ラウンド」で別の N 案を出す。

## いつ使うか

- dev-auto:run のフェーズ 3 で、入力がテーマ・課題だけで具体的な機能が無く、「アイデア出しから始める」になったとき（引数 `<run-id>`。全自動モードなら `<run-id> --auto`）
- 他のスキル（イベント参加用のラッパーなど）から、テーマ・制約・評価基準・出力先を渡されて呼ばれたとき
- 単独で「このテーマで何を作れるか何案か出して比べたい」と言われたとき

引数（指示文の中で渡してよい。無いものは既定値か「指定なし」）:

| 引数 | 内容 | 既定 |
|---|---|---|
| テーマ・課題 | 何についての案か（文・ファイルパス） | 必須。run から呼ばれたら input.md |
| 制約 | 期間・人数・使う / 使わない技術・禁止事項 | 指定なし |
| 評価基準 | 案を比べる観点（配点があれば配点） | 下の既定の軸 |
| 中核テーマ・技術 | 案の中心に置くべきテーマ・技術 | 指定なし |
| 件数 `--count N` | 案の数 | 5 |
| 追加の制約 | 呼び出し元が足す生成ルール（1 行ずつ） | なし |
| 出力先 `--out <dir>` | 案ファイルを置くディレクトリ | `docs/dev-auto/ideas/<topic>/` |
| 追加の選択肢 | 手順 3 の 1 問目に足すもの（1 つまで。ラベルと説明） | なし |
| `--auto` | 選択を訊かずに推奨案を採る | なし |

`<topic>` はテーマから作る英小文字ケバブの slug（3〜5 語）。run から呼ばれたときは run の slug を使う。

## 進め方

鉄則: 案を選ぶのはユーザー。確認はすべて AskUserQuestion で行い、推奨を先頭に「(Recommended)」付きで置く。平文で質問して返事を待たない。`--auto` のときだけ、訊かずに推奨案を採る。

### 1. 条件をそろえる

1. テーマ・課題・制約・評価基準・中核テーマ・技術を、引数・input.md・（あれば）`docs/dev/context.md` から読み取る。書かれていない項目は「指定なし」とし、推測で埋めない
2. 出力先を決める。出力先に既に案ファイルがあれば上書きせず、`<出力先>/round-N/`（N は 2 から空いている番号）を今回の出力先にする

### 2. N 案を一度で生成する

**書く前に、N 案の一行要約と「対象ユーザー・入力の種類・UI の形・AI の役割」の表を作り、次のルールを満たすか自己点検する。** 満たさなければ一行要約の段階で入れ替える。

- 多様性: N 案で **対象ユーザー・入力の種類・UI の形・AI の役割** がすべて異なる（同じ値が 2 案に出ない）
- 「定番」の案（その分野で誰もが最初に思いつく案。例: 議事録の要約・書類の読み解き・チャットで質問に答えるだけのもの）は **1 案まで**
- 中核テーマ・技術が指定されているときだけ: それが **プロダクトの中心にある案を 2 案以上**。中心とは「それが無いとプロダクトが成り立たない」こと。外部 API を 1 回呼ぶだけで置き換えがきくものは中心とみなさない
- 制約（期間・人数・必須技術・禁止事項）の中で MVP が完成する大きさにする
- 呼び出し元から渡された追加の制約をすべて満たす
- ラウンド 2 以降: 既出の案と対象・入力・UI・AI の役割の組み合わせが重ならない

続けて `<出力先>/<slug>.md` を N 個書く。見出しは次のとおり（1〜5 は要件の5点。dev-auto:refine の品質チェックがそのまま通る書き方にする）。

```markdown
# <案の名前>（一行要約）

## 1. 目的（誰の何を解決するか）
## 2. スコープ（やること / やらないこと。制約の中で完成する MVP）
## 3. 振る舞い（主要なユースケースと、その入出力・画面の動き）
## 4. 受け入れ条件（観察できる・自動で判定できる形。可能なら数値）
## 5. 扱うデータ（エンティティ名と主な項目）
## テーマ・評価基準との対応（評価基準ごとに 1 行。基準が無ければテーマとの対応だけ）
## AI の役割 / 技術の活かし方
## デモ / 価値の見せ場（短い時間で価値が伝わる場面）
## リスクと削る順序（時間が足りないとき、どこから削るか）
```

続けて `<出力先>/README.md` に比較表と推奨を書く（round-N のときは README.md の末尾に「ラウンド N」の節を足す）。

- 列: 評価基準が渡されていればその基準、無ければ既定の軸 **テーマ適合・独自性・インパクト・実現性・見せやすさ**（各 5 段階）と合計
- **採点基準** を表の下に書く。各軸の 5・3・1 の目安を 1 行ずつ（例: テーマ適合 5 = 中核テーマ・技術が無いと成り立たない / 3 = 使うが置き換えられる / 1 = 関係が薄い）
- 一行要約の自己点検表（対象・入力・UI・AI の役割）も載せる
- 推奨 1 案と理由。理由は **示されたテーマ・評価基準への適合を最優先** にし、次に配点の大きい軸で説明する

並列化（任意）: 既定は Claude 自身が 1 パスで書く。案ごとの深さが欲しいときだけ、自己点検を済ませた表を作ってから、案ごとにサブエージェント（sonnet 目安）を 1 つずつ並列で立てて本文を書かせる。各サブエージェントには条件と担当行だけを渡し、「`git stash` を使わない」と書く。

### 3. 案を選ぶ

`--auto` なら訊かない。推奨案を選んだものとして扱い、run から呼ばれたときは `docs/dev-auto/<run-id>/decisions.md` に「ideate: 推奨案 <slug> を採用（auto。理由）」を 1 行足す。

それ以外は AskUserQuestion で訊く。**1 問の選択肢は最大 4 つ**（AskUserQuestion の上限）なので、次の決まった形にする。どの問いにも自動で付く「Other」には自由記述で答えてよい。

1 問目（呼び出し元の追加の選択肢が無いとき）:

1. 「推奨案 <案の名前>（Recommended）」→ 推奨案を選んだものとする
2. 「別の案を選ぶ」→ 2 問目へ
3. 「組み合わせる・手直しする」→ 何をどう変えるかを AskUserQuestion で訊き、新しい案ファイルを作るか既存ファイルを直す。直したら5点がそろっているか確かめ、選んだ案として扱う
4. 「もう 1 ラウンド」→ 手順 1 の round-N のルールで新しい出力先を決め、手順 2 を同じ条件で行い、もう一度この手順で訊く

1 問目（呼び出し元の追加の選択肢があるとき。追加は 1 つまで）:

1. 「推奨案 <案の名前> で進める（Recommended）」
2. 呼び出し元の追加の選択肢（ラベルと説明はそのまま）→ 推奨案を選んだものとし、追加の選択肢が選ばれたことも返す
3. 「別の案・組み合わせ」→ 2 問目へ（組み合わせ・手直しは 2 問目の Other に書いてもらい、上の 3 と同じに扱う）
4. 「もう 1 ラウンド」→ 上の 4 と同じ

2 問目「どの案にしますか？」: 推奨案以外の案を合計点の高い順に最大 4 つ並べる（5 案なら残りの 4 案ちょうど。6 案以上なら上位 4 案で、それ以外の案は Other に案の名前を書けば選べると説明に書く）。

### 4. 結果を返す

- どの道筋で終わっても（推奨案・別の案・組み合わせ・追加の選択肢・`--auto`）、呼び出し元に次の 2 つを必ず返す。最後の出力に `chosen: <案ファイルのパス>` と `extra_option: <選ばれた追加の選択肢のラベル | none>` の 2 行で書く
  - 選んだ案ファイルのパス（追加の選択肢が選ばれたときは推奨案のパス）
  - 追加の選択肢が選ばれたか
- 呼び出し元はこの 2 行を読んで次へ進む。run から呼ばれたときは state.md の `ideas_dir` に出力先（round を含まない最初のディレクトリ）を書く
- 単独利用のときは、次の一歩として `/dev-auto:dev-auto <案ファイルのパス>` を示す（起動は訊かない。呼び出し元が無いときだけ示す）

## 成果物

- `<出力先>/<slug>.md` × N（既定 `docs/dev-auto/ideas/<topic>/`。ラウンドを重ねたら `round-N/`）
- `<出力先>/README.md`（採点基準つきの比較表・自己点検表・推奨）
- 選んだ案ファイルのパス（呼び出し元への戻り値）

## 完了チェックリスト

- [ ] 書く前に一行要約と自己点検表を作り、対象・入力・UI・AI の役割がすべて異なる
- [ ] 定番の案が 1 案以下。中核テーマ・技術が指定されていれば、それが中心の案が 2 案以上
- [ ] 各案に5点の見出しと、テーマ・評価基準との対応 / AI の役割 / 見せ場 / 削る順序がある
- [ ] 受け入れ条件が観察・自動判定できる形で、扱うデータにエンティティ名と主な項目がある
- [ ] 比較表に採点基準があり、推奨の理由がテーマ・評価基準への適合を最優先している
- [ ] 選択を AskUserQuestion で行った（`--auto` では推奨案を採って記録した）
- [ ] 選んだ案ファイルのパスを返した

## 次のステップ

- dev-auto:run から呼ばれたとき: run が選んだ案を dev-auto:refine の品質チェックに通し、外部仕様（dev-auto:spec）へ進む
- 単独利用: `/dev-auto:dev-auto <案ファイルのパス>`

## やらないこと

- 案づくりを反復ループ・ペルソナの多段レビューで回さない（一発生成。足りなければ「もう 1 ラウンド」）
- 案の選択をユーザーの代わりに決めない（`--auto` のときだけ推奨案を採る）
- 平文で質問して返事を待たない（確認は AskUserQuestion で行う）
- 既存の案ファイルを上書きしない（`round-N/` に分ける）
- このスキルの中でアプリのコードを書かない。頼まれていないコミット・プッシュをしない。`git stash` は使わない
