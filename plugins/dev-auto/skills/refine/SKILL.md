# 要件を詰める（refine）

入力を「目的・スコープ・振る舞い・受け入れ条件・扱うデータ」の5点の PRD にするスキル。そろっている点は訊かず、**足りない・弱い点だけ** を訊く。訊くときは既存コードや入力から推奨案を作って先頭に置くので、ユーザーは選ぶだけで進められる。

## いつ使うか

- dev-auto:run のフェーズ 3 から、引数 `<run-id>` 付きで呼ばれたとき（全自動モードなら `<run-id> --auto`）
- dev-auto:run から `<run-id> --gate <案ファイル>` で呼ばれたとき（dev-auto:ideate で選んだ案を品質チェックに通す。チェックが通れば何も訊かない）
- 単独で「この要望を PRD にしたい」と言われたとき。引数の要件（指示文 / ファイル / issue URL）から run-id（`YYYYMMDD-<slug>`）を作り、`docs/dev-auto/<run-id>/` を作業場所にする（state.md は作らなくてよい）

## 進め方

鉄則: 要件を決めるのはユーザー。確認はすべて AskUserQuestion で行い、推奨を先頭に「(Recommended)」付きで置く。平文で質問して返事を待たない。`--auto` のときだけ、訊かずに仮定で埋める。

### 1. 入力を読む

- run から呼ばれたとき: `docs/dev-auto/<run-id>/input.md`（`--gate` なら案ファイル）と state.md を Read する
- 単独利用: 引数の内容を `docs/dev-auto/<run-id>/input.md` に保存してから読む
- `docs/dev/context.md` があれば読む

### 2. 5点を評価する

各点を **ある / 弱い / 無い** で判定し、根拠（入力のどこに書いてあるか）を 1 行で控える。

| 点 | 「ある」と言える条件 | 「弱い」の例 |
|---|---|---|
| 1. 目的 | 誰の・何の課題を解決するかが書かれている | 「便利にしたい」だけ |
| 2. スコープ | やること と **やらないこと** が分かる | やらないことが無い |
| 3. 振る舞い | 主要なユースケースと入出力・画面の動きが分かる | 機能名だけ |
| 4. 受け入れ条件 | 観察できる・自動で判定できる基準がある | 「使いやすいこと」 |
| 5. 扱うデータ | 保存・表示・変更するエンティティ名と主な項目が分かる | 「ユーザー情報」だけ |

入力が既存コードへの変更（既存の機能・画面・API・ファイル名に触れている、`project_kind: existing` で追加・改修の話）なら、ここで既存コードを調べる。関係するファイル・データ構造・似た機能の作り方を Grep / Read で確かめ（広く探すときは haiku のサブエージェントに任せてよい。「`git stash` を使わない」と書く）、弱い・無い点の推奨案を具体的にする（例: 「既存の `Task` モデルに `due_at` を足す」）。

### 3. 足りない点だけを訊く

`--auto` なら手順 3 は行わず、手順 3b へ。

全点が「ある」なら訊かずに手順 4 へ。それ以外は、弱い・無い点だけを AskUserQuestion で訊く。

- 1 回の呼び出しに最大 4 問をまとめる。5 問以上あるときは、目的 → スコープ → 振る舞い → 受け入れ条件 → データの順で 2 回に分ける
- 各問の先頭の選択肢は、入力・既存コードから作った推奨案（「(Recommended)」付き）。残りは現実的な代案 1〜2 個
- 最後の問いの選択肢に「もっと深く壁打ちしたい」（説明: tsumiki の対話型スキルで時間をかけて詰めます）を入れてよい。選ばれたら、新しい機能・アイデアの段階なら `tsumiki:dcs:feature-rubber-duck`、既存コードへの追加・改修なら `tsumiki:dcs:incremental-dev` を、入力の要約を引数にして呼ぶ。出力された PRD（複数のアプローチ別 PRD なら AskUserQuestion で 1 つ選んだもの）の内容を prd.md に取り込み、手順 4 へ進む。これは既定の道筋ではなく、ユーザーが選んだときだけ使う

回答を各点に反映する。Other で書かれた回答はそのまま使う。

### 3b. 全自動モード（`--auto`）の補完

質問はしない。入力・既存コード・`docs/dev/context.md` から、弱い・無い点を推測で埋める。迷ったら小さく保守的な案（スコープを狭く、既存の慣習に合わせる）を選ぶ。埋めた内容は prd.md の「仮定」に「〜と仮定した（理由）」の形で 1 行ずつ書き、仕様に効くものを `docs/dev-auto/<run-id>/decisions.md` に 1 行ずつ足す（フェーズ欄は refine、根拠に「auto」）。既存コードへの改修でアプローチが複数考えられるときは推奨案を選び、選ばなかった案を「検討した他の案」に 1 行ずつ書く。

### 4. prd.md を書く

`docs/dev-auto/<run-id>/prd.md` に書く（`--gate` で案ファイルがチェックを通ったら、案ファイルをそのまま使い prd.md は作らない）。

```markdown
# <タイトル>

## 1. 目的
## 2. スコープ
### やること
### やらないこと
## 3. 振る舞い
## 4. 受け入れ条件
## 5. 扱うデータ（エンティティ: 主な項目）
## 仮定（「〜と仮定した（理由）」）
## 未決事項（spec で決める・ユーザーに確かめたい点）
## 検討した他の案（あれば）
## 出典（input.md / 案ファイル / 参照した既存コード）
```

### 5. 品質チェック

返す前に次をすべて満たすか確かめる。満たさない点は直す（通常モードで推奨案が作れないときだけ、その点を AskUserQuestion で 1 回訊く。`--auto` では仮定で直す）。

- [ ] 受け入れ条件がすべて **検証できる**（「<操作・入力> すると <観察できる結果>」の形、または自動テストで判定できる数値・状態）。「使いやすい」「速い」だけの条件が無い
- [ ] 扱うデータに **エンティティ名と主な項目** がある（保存しない場合は「保存するデータなし」と明記）
- [ ] スコープに **やらないこと** が 1 つ以上明示されている
- [ ] 目的に「誰の」「何の課題」の両方がある

`--gate` のときは、案ファイルがすべて満たせば何も訊かず案ファイルのパスを返す。満たさない点があれば、その点だけを手順 3（`--auto` なら 3b）で埋めて prd.md を作る。

### 6. 結果を返す

- run から呼ばれたとき: state.md の `prd_path` に prd.md（`--gate` で通過したら案ファイル）のパスを、`refine_mode` に `asked`（質問した）/ `auto`（全自動で補完）/ `gate`（案ファイルがそのまま通過）/ `deep-dive`（tsumiki で壁打ちした）を書く。ログに 1 行足す
- 単独利用: prd.md のパスと、次の一歩として `/dev-auto:dev-auto docs/dev-auto/<run-id>/prd.md` を示す

## 成果物

- `docs/dev-auto/<run-id>/prd.md`（5点・仮定・未決事項）
- `--auto` のとき: decisions.md に足した仮定
- state.md の `prd_path` と `refine_mode`（run から呼ばれたとき）

## 完了チェックリスト

- [ ] 5点をある / 弱い / 無いで評価し、根拠を控えた
- [ ] 既存コードへの変更なら、既存コードを調べて推奨案を具体的にした
- [ ] 弱い・無い点だけを AskUserQuestion で訊いた（1 回最大 4 問、推奨案が先頭）。`--auto` では訊かずに仮定を記録した
- [ ] 品質チェック（検証できる受け入れ条件・エンティティと主な項目・やらないこと）を通した
- [ ] `prd_path` と `refine_mode` を state.md に書いた（run から呼ばれたとき）

## 次のステップ

- dev-auto:run から呼ばれたとき: run が関係判定・分割判定を行い、dev-auto:spec へ進む
- 単独利用: `/dev-auto:dev-auto docs/dev-auto/<run-id>/prd.md`、または外部仕様だけ固めるなら dev-auto:spec

## やらないこと

- そろっている点を訊き直さない
- 平文で質問して返事を待たない（確認は AskUserQuestion で行う）
- tsumiki の対話型スキル（feature-rubber-duck / incremental-dev）を既定で呼ばない（ユーザーが「もっと深く壁打ちしたい」を選んだときだけ）
- 外部仕様（画面・API の細部）までここで決めない（それは dev-auto:spec）
- アプリのコードを書かない。頼まれていないコミット・プッシュをしない。`git stash` は使わない
