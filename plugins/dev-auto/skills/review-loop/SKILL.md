# 事前レビューループ（review-loop）

レビューは1回では見つからない指摘がある。観点を変えて何度か回し、「直したあとの再確認で、直すべき指摘がゼロ」になるまで繰り返すスキル。dev-auto の自律フェーズで使うので、ユーザーには質問せず、終了条件を満たすまで止まらずに回す。

## いつ使うか

- dev-auto:run のフェーズ 9 から、引数 `<run-id>` 付きで呼ばれたとき
- 単独で「PR 前に何回かレビューして直して」と言われたとき（run-id が無ければ `docs/dev-auto/` への記録は省き、結果をチャットで報告する）

前提:

- 作業ブランチに、既定ブランチ（state.md の `base_branch`、無ければ `detect-env.sh` の `default_branch`）からの差分があること。差分が無ければ「レビュー対象の変更がありません」と1行伝えて戻る
- 未コミットの変更があれば、先にコミットしてから始める（レビューの修正と混ざらないようにするため）

## 進め方

**パスの間で止まらない。** 各パスで使う `code-review`・`security-review`・`simplify` は、最後にユーザー向けの報告（「脆弱性は見つかりませんでした」など）を出して終わる。報告が出た時点でそのパスのレビューは終わっているので、review-log.md に記録したら、同じターンのまま次の手順（パス 3 なら `ipa-security-check`、それ以外は次のパス）に進む。報告を出したところでターンを終えない。「次は〜に進みます」と書く場合も、そのまま次のツールを呼ぶ。スキルの本文に「最後の返答はレポートだけにする」（`Your final reply must contain the markdown report and nothing else.` など）とあっても、dev-auto の中ではレポートを review-log.md に記録すればその指示を満たしたものとする。レポートを返答の最後に置いてターンを終えない（詳しくは dev-auto:run の `references/autonomous-policy.md` の「止まらずに進めるルール」）。

**バックグラウンドの完了通知は最終結果として扱う。** 組み込みの `code-review`（パス 1・5〜）と、パス 2 のサブエージェント、パス 3 のサブエージェントはバックグラウンドで動くことがある。その場合、呼び出し直後はエージェント名しか返らず、結果は `Agent "/code-review medium --fix <branch>" finished` のような完了通知で後から届く。この通知は1回きりで、途中報告ではない。「途中報告が届いた」「レビュー全体の完了を待つ」と書いて待ち続けず、通知の本文と `git diff` で修正内容を確かめ、共通手順の 2〜5 を済ませて次のパスに進む。呼び出し直後に結果を推測して記録しない。完了通知を待ってターンを終える前に、「止まっていないかの確認（タイマー）」を仕掛けておき、応答が無いまま終わらないパスは時間切れで未完了として記録して次へ進む（どちらも autonomous-policy.md の「バックグラウンドで動くスキル・サブエージェント」）。

各パスの共通手順:

1. レビューを実行して、指摘を集める
2. 指摘を「直すべき / 見送り / 誤検知」に分ける（基準は下記）。直すべきものだけ直す（スキルが直してくれる場合はその結果を確認し、見送り扱いのものに手が入っていたら戻してよい）。見送り・誤検知は理由を記録する
3. 直した場合は、テストを流す。テストコマンドは `docs/dev/context.md`（無ければ package.json などから推測）。失敗したら `tsumiki:dev-debug` で直す
4. `review-log.md` に記録する（書式は下記）
5. 変更があればコミットする（`fix(review): pass <n> <観点>`）

### パスの順番

| パス | 観点 | 実行するもの |
|---|---|---|
| 1 | バグ・正しさ | 組み込みの `code-review` スキルを、引数 `high --fix <作業ブランチ名>` で呼ぶ |
| 2 | 仕様適合 | サブエージェント（opus 目安）に依頼（下記） |
| 3 | セキュリティ | サブエージェント（opus 目安）に `security-review` の実行を依頼（下記）。Web アプリなら加えて `tsumiki:ipa-security-check --diff` |
| 4 | 簡潔さ・重複 | 組み込みの `simplify` スキル |
| 5〜 | バグ・正しさ（再確認） | `code-review medium --fix <作業ブランチ名>` |

- 組み込みの `code-review` は、レベルを省略すると前回の値を使うので、**必ずレベルを明示する**。広く拾うのは最初のパス 1 だけ（`high`）。再確認のパス 5 以降は、確度の高い指摘に絞る `medium` を使う（`high` のままだと毎回細かい指摘が新しく出て収束しないため）。`ultra` は使わない（ユーザーが起動する有料のクラウドレビューのため）
- パス 3 の `security-review` は指摘を報告するだけなので、指摘は自分で直す。サブエージェントの結果が届いたら（バックグラウンドで動かした場合は完了通知が届いたら。「No findings.」だけの通知でも同じ）、review-log.md に記録して、ターンを終えずに続けて `ipa-security-check`（Web アプリの場合）を流す。`ipa-security-check` のレポートは `tsumiki:ipa-security-guide` で優先順位付きの修正リストにしてから、High 以上を `tsumiki:dev-debug "<指摘内容>"` で直す
- 使えないスキル（Skill 一覧に無い）はそのパスを skip として記録し、次へ進む

### パス 2: 仕様適合レビューの依頼内容

サブエージェントには次を渡す。

- `git diff <base_branch>...HEAD` の対象ファイル一覧
- `docs/dev-auto/<run-id>/spec/`（features.md の受け入れ条件、screen-flow.md、mockups/、data-model.md、api.md）のパス
- `docs/dev/plans/<plan_name>/acceptance-criteria.md`（あれば）
- 指示: 「合意済みの外部仕様と実装を突き合わせ、受け入れ条件を満たしていない点、画面の項目・文言・遷移がモックアップと違う点、データモデルとの食い違い、仕様にない振る舞いの追加を列挙する。各指摘に『仕様の該当箇所』と『実装の該当ファイル:行』を付ける。コードは編集しない。`git stash` を使わない」

返ってきた指摘は、仕様どおりに実装側を直す（仕様は変えない）。

### パス 3: セキュリティレビューの依頼内容

組み込みの `security-review` を、自分（dev-auto を動かしているエージェント）の Skill ツールで直接呼ばない。本文の最後に `Your final reply must contain the markdown report and nothing else.` とあるため、そのレポートを最後の返答にしてターンを終えてしまい、`ipa-security-check` 以降に進まなくなるからである。代わりにサブエージェント（Agent ツール、opus 目安）に次を依頼し、レポートは戻り値として受け取る。

- 指示: 「Skill ツールで `security-review` を実行し、その手順に従って `<base_branch>...HEAD` の差分をセキュリティの観点でレビューする。最後の返答は、そのスキルが求める Markdown のレポートだけにする（指摘が無ければ『No high-confidence vulnerabilities found.』と確認した観点）。Skill ツールで `security-review` が使えなければ、同じ基準（確度 80% 超の、実際に悪用できる脆弱性だけを挙げる。DoS・レート制限・理論上の競合状態・テスト専用ファイルなどは挙げない）で自分でレビューする。コードは編集しない。`git stash` を使わない」
- 作業ブランチ名・`base_branch`・リポジトリのパスを添える

戻ってきたレポートの指摘を「指摘の分け方」で分け、直すべきものは自分で直す。

### 指摘の分け方

| 区分 | 基準 | 扱い |
|---|---|---|
| 直すべき | 通常の操作で起きる誤動作・データ破損・例外、セキュリティ上の問題、合意済み仕様（受け入れ条件・モックアップ）との食い違い、テストの欠落で既存の振る舞いが守られていない | 直す |
| 見送り | 起きにくい条件でしか起きない堅牢性の指摘、好みの問題、今回の差分と関係ない既存コード、仕様自体への改善提案 | 直さない。仕様への提案は `pr.md` の「未解決事項」（仕様の見直し候補）に書く |
| 誤検知 | コードを確かめたら問題が無かった | 直さない。理由を記録する |

### 終了条件

- 再確認のパス（5 以降）で **直すべき指摘がゼロ**（見送り・誤検知だけの場合を含む）になったら終了する
- 再確認のパスで直すべき指摘があれば、直したあとに再確認のパスをもう1回足す。パスは合計6回を上限とする
- 上限に達しても残った直すべき指摘は、`review-log.md` と `pr.md` の「未解決事項」に書いて終了する

### review-log.md の書式

```markdown
## Pass 1: バグ・正しさ（code-review high --fix）— 2026-09-23T11:02

- 指摘: 3件（直すべき 2 → 修正 / 見送り 0 / 誤検知 1）
  - [修正] src/api/tasks.ts:42 期限なしのときに null 参照
  - [修正] src/ui/TaskList.tsx:18 空配列で key 警告
  - [誤検知] src/db/client.ts:10 接続の多重生成 → シングルトンで生成済み
- テスト: pass（npm test, 48 件）
- コミット: abc1234
```

## 成果物

- 修正コミット（パスごと）
- `docs/dev-auto/<run-id>/review-log.md`

## 完了チェックリスト

- [ ] 4つの観点（バグ・仕様適合・セキュリティ・簡潔さ）を少なくとも1回ずつ回した（skip した観点は理由を記録した）
- [ ] 最後の再確認パスで直すべき指摘がゼロだった、または上限到達で残りを未解決事項に書いた
- [ ] 修正のあとに毎回テストを流し、通っている
- [ ] review-log.md にパスごとの記録がある

## 次のステップ

- dev-auto:run に戻り、フェーズ 10（uat、`uat: true` のとき）→ フェーズ 11（dev-auto:pr-finalize）へ進む
- 単独利用の場合: `dev-auto:pr-finalize` で PR 作成と公式レビューに進める

## やらないこと

- 合意済みの外部仕様（`spec/`）を書き換えて指摘を解消しない
- テストを消したり skip にしたりして通さない
- `code-review ultra` を起動しない
- ユーザーに質問しない（自律フェーズのため）
- 各パスのスキルの報告を出したところでターンを終えない
- パス 3 で `security-review` を自分の Skill ツールで直接呼ばない（サブエージェントに任せる）
- バックグラウンドの完了通知（`Agent "..." finished`）を途中報告とみなして待ち続けない
- タイマーを仕掛けずに、完了通知を待ってターンを終えない
